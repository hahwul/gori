가이드

접근 제어 테스트

접근 제어 결함은 대부분 세션 하나만 봐서는 드러나지 않습니다. 관리자로 로그인한 상태에서 /admin/users가 목록을 돌려주면 정상으로 보이지만, 익명 클라이언트나 읽기 전용 사용자, 다른 테넌트가 무엇을 받는지는 알 수 없습니다. Authorize는 이미 캡처해 둔 요청을 여러 아이덴티티로 재전송하고, 각 응답을 기준선(baseline)과 비교합니다. 기준선과 같은 응답을 받는 아이덴티티가 있다면 인가 우회일 가능성이 높습니다. Burp의 Autorize / Auth Analyzer, AuthMatrix에 해당하는 gori의 도구입니다.

Authorize 탭은 기본적으로 바 밖에 있습니다. **0**을 누르고 "auth"를 입력하거나, 커맨드 팔레트(Ctrl-P → Go to Authorize)를 쓰거나, Preferences(Ctrl-,) → Network & Tabs → Tabs에서 아홉 슬롯 중 하나를 내주세요.

아이덴티티란

아이덴티티는 세션 슬롯입니다. 이름, 재전송 직전에 캡처된 요청에 덧씌우는 정적 헤더 오버레이, 바인딩 값이 그 슬롯에 속하는 extract 규칙으로 이루어집니다. gori 어디서나 같은 슬롯을 씁니다. Authorize 탭은 모든 슬롯으로 재전송하고, Repeater나 Fuzzer 전송은 활성 슬롯 하나로 나갑니다(아래 세션 슬롯 참고).

필드 동작
set 헤더를 upsert합니다. 같은 이름의 헤더(대소문자 무시, 원래 표기 유지) 값을 모두 교체하고, 없으면 추가합니다
remove 같은 이름의 헤더를 모두 제거합니다

"anonymous" 아이덴티티는 Cookie와 Authorization을 제거합니다. "admin"이나 "low-priv" 아이덴티티는 그 자리에 다른 세션의 값을 넣습니다. API라면 X-Api-Key를 설정하면 됩니다. 오버레이는 헤더 줄만 건드립니다. 요청 라인, 바디, Content-Length는 바뀌지 않으므로, 같은 요청을 자격증명만 바꿔 비교합니다.

탭에서 i를 누르면 아이덴티티 카드가 열립니다. 새 프로젝트는 두 개로 시작합니다. as-captured(오버레이 없음)와 anonymous(Cookie, Authorization 제거)입니다.

키 아이덴티티 카드에서
↑ / ↓ 아이덴티티 선택
a 추가
e / ↵ 편집
d 삭제
b 이 아이덴티티를 기준선으로 지정
esc 닫기

추가·편집 폼에는 필드가 네 개 있습니다. 이름(고유해야 하고 대소문자를 구분하지 않고 비교하며, 세 surface 모두 중복을 거부합니다), remove할 헤더(drop headers:, 쉼표로 구분), set할 헤더(한 줄에 Name: value 하나씩), refresh before(off, jwt-exp, ttl=10m. 슬롯 갱신 참고)입니다. 슬롯의 갱신 단계는 그 바로 윗줄에 읽기 전용으로 표시됩니다. ⇥로 필드를 옮기고 ↵로 저장합니다(set 헤더 편집기 안에서는 줄바꿈을 넣습니다). 이름이 유효한 토큰이 아니거나 값에 CR/LF가 들어간 줄은 거부되며, 오류 메시지에 해당 줄이 표시됩니다.

아이덴티티는 프로젝트에 저장되므로 gori run authorize와 MCP 도구도 여기서 설정한 집합을 기본으로 씁니다. 목록에는 헤더 이름만 표시되므로 세션 쿠키가 화면에 보이지 않습니다. 폼에는 값이 보입니다.

화면에 이미 있는 결과는 이전 집합에서 나온 판정이므로, 아이덴티티 집합을 바꾸면 모두 다시 대기 상태가 됩니다.

세션 슬롯: 하나의 목록, 두 명의 독자

이 탭은 요청 하나를 모든 슬롯으로 보내 답을 비교합니다. 다른 전송 경로는 모두 슬롯 하나를 씁니다. 슬롯을 고르면 이후 요청이 모두 그 슬롯으로 나갑니다.

활성 슬롯 고르기와 목록 편집은 별개의 동작입니다.

표면 활성 슬롯 고르기 목록 편집
TUI Ctrl-P → Session slot, 또는 session:NAME 칩 클릭 이 탭에서 i
gori run 보내는 명령에 --slot NAME gori run session list | show | add | from-flow | from-request | edit | rm | baseline | refresh
MCP set_active_session_slot list_session_slots, create_session_slot, update_session_slot, delete_session_slot

활성 슬롯이 send_request, Repeater/Fuzzer 전송, 인터셉트 forward에서 바꾸는 것은 두 가지입니다.

  • 그 슬롯의 헤더 오버레이가 $BIND.NAME 치환 이후 최종 와이어 바이트의 헤더 줄에만 적용됩니다. 그래서 Content-Length는 바뀌지 않고 본문은 바이트 그대로입니다.
  • $BIND.NAME이 그 슬롯의 바인딩 테이블에서 해소됩니다. 슬롯에 속한 extract 규칙은 그 슬롯의 테이블에 쓰고, 어느 슬롯에도 속하지 않은 규칙은 전역 테이블에 씁니다. 그래서 저장된 문자열 Authorization: Bearer $BIND.SESSION 하나가 admin 슬롯에서는 admin의 토큰, low-priv에서는 저권한 사용자의 토큰이 됩니다.

슬롯 헤더는 $BIND.NAME과 $GEN.NAME만 해소합니다. 헤더 속 $ENV.KEY는 적힌 그대로 나가며, gori run session add/edit와 MCP의 슬롯 쓰기는 헤더에 그런 토큰이 있으면 경고합니다. 값을 직접 적으세요.

활성 슬롯이 하지 않는 일은 세 가지입니다.

  • Authorize 실행에는 적용되지 않습니다. 이 탭은 전송마다 아이덴티티를 직접 지정하므로, 실행은 활성 슬롯을 무시합니다. 적용된다면 활성 슬롯의 Cookie가 쿠키를 없애는 아이덴티티까지 포함해 모든 아이덴티티를 덮어쓰고, 대기 중인 행이 모두 있지도 않은 우회를 보고합니다. 위의 두 번째 항목은 여전히 적용됩니다. 각 아이덴티티의 오버레이가 씌워질 때 $BIND.NAME은 그 아이덴티티의 바인딩 테이블에서 해소되므로, admin과 low-priv 양쪽의 Cookie: session=$BIND.SESSION은 서로 다른 두 세션으로 나갑니다.
  • 저장되지 않습니다. 프로젝트를 다시 열거나 gori mcp가 새로 연결되면 캡처된 그대로 시작합니다. 슬롯의 값은 메모리 전용이라, "admin이 활성"을 복원하면 $BIND.SESSION이 리터럴인 오버레이가 나가 원인을 알 수 없는 401을 받습니다.
  • as-captured는 두 가지 의미 모두에서 기준선입니다. 활성 슬롯이 없으면 어떤 바이트도 바뀌지 않으므로, 슬롯이 생기기 전에 쓰인 프로젝트와 플레이북은 이전처럼 동작합니다.

여기에는 cookie jar가 없습니다. 슬롯에는 직접 쓴 헤더와 gori가 관찰한 값이 들어 있습니다. --bind-from은 지정한 플로우 하나를 재생해 그 값을 채우고, 슬롯의 갱신 단계는 목록에 넣어 둔 Repeater 세션을 재생합니다.

슬롯 갱신

슬롯은 스냅샷이라서 긴 실행 도중에 토큰이 만료될 수 있습니다. 슬롯에 갱신 단계, 즉 로그인하는 Repeater 세션을 순서대로(예: csrf-fetch → login) 붙이면 슬롯이 스스로 다시 인증합니다. 각 단계의 응답은 슬롯의 extract 규칙을 거치고, 그 규칙이 슬롯을 다시 바인딩합니다. 단계는 슬롯 자신의 $BIND.NAME 값을 해소하고 슬롯 헤더 오버레이는 싣지 않으므로, 교체 대상인 만료된 자격 증명이 로그인 요청에 실리지 않습니다. 일회용 코드를 요구하는 로그인에는 $GEN.TOTP를 넣으면 갱신할 때마다 새 코드를 만듭니다.

표면 단계 추가 지금 갱신 정책
TUI Repeater의 로그인 서브탭에서 Ctrl-P → Use as refresh for slot… 세션 슬롯 피커의 행에서 Ctrl-R 아이덴티티 폼(이 탭의 i)의 refresh before 필드
gori run session edit NAME --refresh 12,14 session refresh NAME --refresh-before
MCP update_session_slot{refresh} refresh_session_slot 없음: off만

refresh before 정책은 슬롯으로 나가는 전송 직전에 갱신을 자동으로 실행합니다. jwt-exp는 슬롯에 바인딩된 JWT의 exp가 30초 이내로 남았을 때, ttl=10m은 마지막으로 성공한 갱신(없으면 슬롯에서 가장 오래된 바인딩) 이후 그 시간이 지났을 때입니다. 갱신 후에도 JWT가 곧 만료되는 상태면 실패로 칩니다. 활성 슬롯뿐 아니라 Authorize 실행이 보내는 모든 아이덴티티에 적용됩니다. 정책은 전송 전에 동작하고 응답을 읽지 않습니다. 이 탭에서 401은 판정일 뿐, 다시 로그인해 재시도하는 계기가 되지 않습니다.

정책은 운영자만 켭니다. TUI의 자동 갱신은 슬롯의 현재 자격 증명을 실어, 사전 scope 검사 없이 단계를 보냅니다. 그래서 gori mcp로 붙은 에이전트는 refresh_before를 off로만 정할 수 있고, 켜진 슬롯의 단계(refresh 목록, 또는 그 Repeater 세션의 요청이나 대상)를 바꾸면 정책이 꺼지며 응답에 그 사실이 표시됩니다. refresh_session_slot으로 단계를 수동 실행할 수는 있으며, 이때도 다른 에이전트 전송처럼 게이트를 거칩니다.

각 갱신 단계는 source refresh(src:refresh, SRC RFRSH)로 History에 남고, 갱신마다 이벤트가 하나 기록되며, session:NAME 칩은 갱신 중에 ⟳, 실패 후에 !를 표시합니다. 실패하면 알림도 뜨고, 전송은 기존 값으로 나갑니다. 자동 갱신이 실패하면 30초 동안 다시 시도하지 않고, 3번 연속 실패하면 수동 갱신이 성공할 때까지 꺼집니다. Repeater 세션이 삭제된 단계는 (deleted)로 목록에 남고 실행되지 않습니다. 값은 프로세스마다 따로 있습니다. TUI에서 갱신해도 실행 중인 gori mcp의 값은 바뀌지 않습니다.

기준선

실행마다 아이덴티티 하나만 기준선이 됩니다. 나머지 아이덴티티는 모두 이 응답을 기준으로 판정됩니다. 기준선으로 지정한 아이덴티티가 없으면(카드에서 b, JSON에서 "baseline":true) 캡처된 요청이 기준선이 됩니다. 이 요청은 원래 세션으로 나갑니다.

실행에는 기준선 외에 아이덴티티가 하나 이상 필요하며, 세 surface 모두 그렇지 않은 실행을 거부합니다. 아이덴티티가 하나뿐이면 기준선을 기준선과 비교할 뿐입니다.

작업 흐름

  1. History에서 시험할 플로우를 선택하고 Space > a(Send flow to… → Send to Authorize)를 실행합니다. Sitemap에서도 같은 동작으로 선택한 엔드포인트의 캡처 플로우를 큐에 넣습니다.
  2. Authorize 탭에서 i를 눌러 비교할 아이덴티티를 구성합니다.
  3. Ctrl-R은 아직 결과가 없는 요청을 모두 재전송하고, ⇧R은 전부 다시 실행하며, t는 커서에 있는 요청을 실행합니다.
  4. 테이블을 읽습니다. 위쪽 패널은 요청당 한 행으로 종합 판정을 보여주고, ⇥로 선택한 요청의 아이덴티티별 상세를 아래 패널에서 확인합니다.

아이덴티티마다 별도 커넥션을 쓰며, 시도마다 핸드셰이크 비용이 듭니다. 커넥션 지향 인증(내부 진단에서 흔한 NTLM, Negotiate)은 메시지가 아니라 커넥션을 인증하므로, 소켓을 재사용하면 Cookie를 제거한 아이덴티티에게도 기준선의 콘텐츠가 나가 존재하지도 않는 우회를 보고합니다.

Ctrl-X로 중지합니다. 중지 플래그는 요청 사이와 아이덴티티 사이에서 확인되므로 다음 전송에서 멈춥니다. 아이덴티티 도중에 잘린 요청은 판정을 내지 않으므로, 일부만 수행된 시도가 "enforced"로 읽히지 않습니다. passive replay가 켜져 있을 때 중지하면 passive도 함께 멈춥니다. 다음에 Ctrl-R을 누르거나, p로 passive를 껐다 켤 때까지 멈춘 채로 있습니다.

판정 읽기

각 아이덴티티의 응답은 세 가지 사실(상태 코드, 디코딩된 바디 크기, SimHash 콘텐츠 지문)로 축약되어 기준선과 비교됩니다. 지문을 만들기 전에 바디를 먼저 디코딩합니다(gzip / deflate / br / chunked).

판정 의미
baseline 이 행이 기준선입니다
different 상태 코드 클래스가 다르고(2xx vs 4xx vs 3xx) 이 아이덴티티가 2xx를 새로 얻지도 않았습니다. 접근 제어가 작동했다는 가장 분명한 신호입니다. 또는 두 리다이렉트가 서로 다른 목적지를 가리킵니다
same 상태 클래스가 같고 바디도 일치합니다. SimHash 거리 3 이내 그리고 크기 차이 10% 이내. 또는 두 리다이렉트가 같은 곳을 가리킵니다
review 상태 클래스는 같은데 바디가 갈립니다. 또는 이 아이덴티티가 기준선이 받지 못한 2xx를 받았거나(403 → 200, 304 → 200), 두 리다이렉트가 쿼리나 프래그먼트만 다른 같은 경로를 가리키거나, 비교할 ETag도 Content-Length도 없는 HEAD·304 쌍이거나, 기준선 자체가 실패했거나 거부(4xx/5xx)되어 기준으로 삼을 것이 없었습니다
error 이 아이덴티티의 전송이 실패했습니다(TLS, DNS, 타임아웃, 거부). 비교된 것이 없습니다

리다이렉트끼리는 바디를 보기 전에 Location으로 판정합니다. 리다이렉트의 바디는 비어 있어서, 위의 세 가지 사실만으로는 인증된 302 → /dashboard와 익명의 302 → /login이 모두 same으로 나옵니다. 두 응답 모두 Location이 있을 때, 완전히 같으면 same, 스킴·호스트·포트·경로가 같고 쿼리나 프래그먼트만 다르면 review(두 아이덴티티 모두 그 자원에 닿았습니다), 그 밖에는 different입니다. 경로는 쓰인 대로 비교하므로 /login과 /login/은 다른 것으로 봅니다.

요청 단위 행은 이를 종합합니다. 기준선이 아닌 아이덴티티 중 하나라도 same이면 BYPASS(TUI 행에는 ⚠ N same으로 표시), 전부 명확히 다르면 enforced, 전송이 전부 실패했으면 error, 그 밖에는 review입니다.

아무 응답도 받지 못한 요청에는 same도 different도 없으므로, 그 둘만으로 집계하면 enforced가 됩니다. 그래서 모든 surface가 이를 error로 구분해 보고합니다. 탭은 행을 error로 칠하고, gori run authorize는 그 행에 [x] error를 출력하며, MCP 판정은 unanswered_count와 함께 error입니다. 실행 전체가 아무것도 비교하지 못했다면(모든 요청이 게이트에 막혔거나 응답을 못 받았다면) CLI는 요약 줄에 그렇게 적고 0이 아닌 코드로 종료합니다. 그래서 종료 코드로 판정하는 스크립트가 죽은 호스트를 막아낸 엔드포인트로 오해하지 않습니다.

SimHash는 숫자와 16진 토큰을 건너뛰므로 크기가 다른 두 페이지가 가깝게 해싱될 수 있습니다. 이 경우는 크기 조건이 걸러냅니다. 10% 여유를 두는 이유는 실제 페이지에 요청마다 달라지는 잡음(CSRF 토큰, 타임스탬프)이 있기 때문이며, 완전 일치를 요구하면 그 잡음이 전부 걸립니다.

판정은 휴리스틱이고 판정 이름은 중립적입니다. 보안상 의미는 그 아이덴티티가 가져야 할 권한에 달려 있고, 그 권한은 운영자만 알기 때문입니다. 저권한 아이덴티티의 same은 우회일 가능성이 높습니다. 두 번째 관리자 세션의 same은 정상입니다. review는 200으로 렌더된 맞춤형 "접근 거부" 페이지와 사용자별로 원래 다른 페이지가 지문으로는 구별되지 않는 경우입니다.

무엇이, 왜 건너뛰어지는가

선택 범위에는 의미 있게 재전송할 수 없는 플로우가 섞일 수 있습니다. gori는 건너뛴 플로우를 빠짐없이 알려 줍니다.

이유 왜 우회 방법
no identity changes them 어떤 아이덴티티도 이 요청의 바이트를 바꾸지 않습니다. 모든 시도가 같은 것을 보내니 응답도 구조상 일치하고, 행은 same으로 읽힙니다 이 엔드포인트가 인증에 쓰는 헤더를 set하거나 remove하는 아이덴티티를 추가하세요
not a safe method to repeat 기본적으로 GET / HEAD / OPTIONS만 재전송합니다. POST / PUT / PATCH / DELETE를 재전송하면 부수 효과가 아이덴티티 수만큼 다시 실행됩니다 --unsafe-methods(CLI), unsafe_methods:true(MCP). 사람이 요청을 직접 고르는 TUI의 수동 큐는 어떤 메서드든 받습니다
never completed 비교할 응답이 캡처에 없습니다 —
answered by gori gori가 이 요청을 직접 처리했습니다. 뒤에 오리진이 없습니다 —
outside project scope 아웃바운드 게이트가 소켓을 열기 전에 대상을 거부했습니다 --allow-unscoped(CLI), allow_unscoped:true(MCP), 또는 스코프 include 규칙 추가
already queued 같은 플로우를 두 번 지정했습니다 —
no flow with that id 지정한 플로우 id가 없습니다(오타이거나 정리된 플로우) —
sent by gori, not the browser 패시브 재전송에만 해당합니다. 브라우징한 것이 아니라 gori 자신의 트래픽(Repeater 전송, 퍼즈 행, 에이전트의 요청)입니다 —

첫 번째 행은 요청에 Cookie가 있는지가 아니라, 어떤 아이덴티티든 요청의 바이트를 바꾸는지를 봅니다. Cookie 검사로는 X-Api-Key 같은 헤더로 인증하는 API를 놓칩니다.

패시브 재전송

p는 무인 재전송을 켭니다. 프록시로 브라우징하는 동안, 완료되었고 스코프 안이며 안전한 메서드이고 최소 한 아이덴티티가 바꾸는 플로우가 자동으로 큐에 들어가 재전송됩니다. 기본은 꺼짐이고 다른 동작으로는 켜지지 않습니다. 이 탭에서 키 입력 없이 대상에 요청을 보내는 기능은 이것뿐입니다.

수동 큐와 달리 패시브에는 스코프 include 규칙이 필요합니다. 하나도 없으면 아무것도 재전송되지 않으며, p를 누를 때 gori가 그 사실을 알려 줍니다. 브라우저 세션은 진단 범위 밖의 호스트에도 많이 닿고, 패시브는 브라우저를 따라갑니다.

패시브는 플로우 id가 아니라 엔드포인트(METHOD + URL)로 중복을 제거합니다. /orders를 열 번 방문해도 다시 큐에 들어가지 않지만, /orders?id=2는 별도 행이 됩니다. 큐는 200개로 제한되며, 제한에 도달하면 알려 줍니다.

탭에는 패시브의 처리 현황이 계속 표시됩니다(N seen · M queued · K skipped (이유)).

헤드리스

# 프로젝트에 저장된 아이덴티티로 캡처 플로우 두 개를 시험
gori run authorize 12 13

# 아이덴티티를 직접 지정하고, id 대신 QL 쿼리로 선택
gori run authorize --query 'host:acme.test method:GET status:200' \
  --identities identities.json --limit 20

identities.json은 탭이 저장하고 MCP 도구가 받는 것과 같은 형식입니다.

[{"name": "anonymous", "remove": ["Cookie", "Authorization"]},
 {"name": "low-priv",  "set": [{"name": "Cookie", "value": "session=…"}]}]

텍스트 출력은 요청당 한 블록입니다. 왼쪽 끝을 훑으며 [!] BYPASS를 찾을 수 있는 헤드라인 뒤에 아이덴티티별 행이 이어집니다.

authorizing 2 requests × 2 identities (as-captured, anonymous) = 4 requests
[!] BYPASS    #1     GET    http://127.0.0.1:8399/admin/users  · 1 of 1 identity matched the baseline
      as-captured         baseline  200  118B     —
      anonymous           same      200  118B     Δ status 200 · size same · time -434 µs

[ ] enforced  #2     GET    http://127.0.0.1:8399/orders
      as-captured         baseline  200  118B     —
      anonymous           different 403  9B       Δ status 200 → 403 · size -109 B · time +272 µs
done · 2 requests replayed · 4 sends · 1 possible bypass

건너뛴 플로우는 아무것도 보내기 전에, 플로우 단위로 먼저 보고됩니다.

skipped 1 flow · 1 no identity changes them
  #1     GET    http://acme.test/pricing  — no identity changes them

TUI를 열지 않고도 슬롯 목록(i 카드가 편집하는 행들)을 관리할 수 있습니다.

gori run session list                       # 이름, 오버레이(값은 [REDACTED]), 소유한 규칙
gori run session add --name low-priv --set 'Cookie: session=…' --rule SESSION
gori run session edit low-priv --clear-set --set 'Cookie: session=new'
gori run session baseline as-captured
gori run session rm low-priv

gori run 프로세스는 보내고 끝나므로 gori run session activate는 없습니다. 대신 전송 명령에서 아이덴티티를 지정하세요. --slot NAME은 send, repeater, repeater send, repeater race, repeater timing, repeater minimize, fuzz, mine, sequence, discover, retest run에서 동작하며, --bind-from이 시드를 재생하기 전에 적용되므로 실행은 시드가 채운 슬롯으로 전송합니다.

--format jsonl은 요청이 끝나는 대로 한 줄에 하나씩 흘려보냅니다. --format json은 버퍼링했다가 마지막에 배열 하나를 냅니다. 둘 다 와이어 크기와 함께 판정이 비교한 디코딩 후 크기를 담습니다. gzip 응답이라면 두 숫자의 자릿수가 달라질 수 있습니다. 전체 플래그는 CLI 레퍼런스에 있습니다.

에이전트에서

MCP 도구 네 개가 같은 엔진을 백그라운드 잡으로 실행합니다. authorize_start(job_id, 예정된 전송 수, 아이덴티티 이름, 스코프 게이트, 건너뛴 목록을 반환), authorize_status, authorize_results, authorize_stop입니다.

authorize_results는 답을 맨 앞에 놓습니다. access_control이 결과를 한 단어로 말하고(BYPASS, enforced, review, error, nothing_sent. 뒤의 둘은 비교된 것이 없다는 뜻), summary가 한 문장으로 풀어 주며, bypasses는 기준선이 아닌 아이덴티티가 기준선의 응답을 받은 요청을 페이징 없이 전부 나열합니다. 40 KB 응답 예산을 넘는 나머지는 bypasses_unshown_ids에 플로우 id로 남고, 자세한 내용은 bypass: true로 표시된 results 행에 있습니다.

슬롯을 관리하는 도구가 여섯 개 더 있습니다. list_session_slots(활성 슬롯을 이름으로 표시하며, 요청하지 않는 한 헤더 값은 [REDACTED]), create_session_slot, update_session_slot, delete_session_slot, set_active_session_slot, refresh_session_slot입니다. set_active_session_slot은 그 서버 프로세스가 살아 있는 동안 다른 모든 도구의 전송이 어떤 아이덴티티로 나갈지 고르고, refresh_session_slot은 슬롯의 갱신 단계를 지금 실행합니다.

실행 한 번은 전송 2,000건으로 제한되며, 상한은 플로우 × 아이덴티티로 셉니다. 500행 쿼리에 아이덴티티 다섯(전송 2,500건)이면 잘라서 실행하지 않고 두 요인을 밝히며 시작 전에 거부합니다. 여기서는 Layer 1 스코프가 엄격합니다. 스코프 밖 대상에는 allow_unscoped:true가 필요합니다.

아무것도 보내지 않은 실행은 증거가 아닙니다

모든 표면이 이 규칙을 지킵니다.

샌드박스나 exclude 규칙이 소켓을 열기도 전에 모든 전송을 거부했거나, 선택한 플로우가 전부 건너뛰어졌다면, gori는 "기준선과 일치한 아이덴티티 없음"이라고 보고하지 않습니다. 아무것도 보내지 않았다고 알립니다. 도중에 중지한 실행은 중지됐다고 알리고, 끝난 요청만 셉니다.

실제 enforced는 재전송한 요청에서 시험한 아이덴티티에 대해 접근 제어가 지켜졌다는 뜻입니다. 다른 엔드포인트, 다른 권한 경계, 모델링하지 않은 아이덴티티는 안전한 것이 아니라 시험되지 않은 것입니다.
