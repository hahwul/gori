설정 레퍼런스

gori는 전역 환경설정을 settings.json에, 각 프로젝트를 자체 SQLite 데이터베이스로 저장합니다. 전체 흐름은 설정 가이드를 참고하세요. 이 페이지는 키 단위 레퍼런스입니다.

저장소 레이아웃

모든 파일은 GORI_HOME 아래에 있습니다($GORI_HOME이 설정되어 있고 비어 있지 않으면 그 값, 아니면 ~/.gori):

Path Contents
settings.json 전역 환경설정
gori.db 기본 프로젝트 데이터베이스
projects/ 이름 붙은 프로젝트마다 하위 디렉터리 하나, 각각 자체 DB 보유
ca/ 루트 CA: root.crt.pem과 root.key.pem
themes/ 사용자 테마
wordlists/ 전역 wordlist 카탈로그: Fuzzer, Miner, Discover, Cookie 크래킹이 쓰는 이름 붙은 목록(소유자 전용 파일)
protos/ gRPC 디스크립터 셋(protoc --descriptor_set_out). 자체 경로를 지정하지 않은 프로젝트가 여기서 읽습니다
active_project 가장 최근에 사용한 프로젝트 마커
gori.log TUI 로그
browser/ Open browser가 띄우는 브라우저 프로필
shell/ Open shell용 CA 번들과 환경
spool/ 실행 중인 fuzz 스윕의 전체 결과(저장하거나 버릴 때까지)
preview/ 외부 뷰어에 넘기는 임시 파일

settings.json

settings.json은 JSON입니다. gori settings / gori settings --edit로 찾거나 편집합니다.

파일이 유효한 JSON이 아니어도 gori는 멈추지 않습니다. stderr(와 TUI 알림)로 알리고, 해당 세션은 기본값으로 실행하며, 덮어쓰기 전에 원본을 settings.json.corrupt로 보관하고, 파일에 적힌 env.syntax는 읽어 냅니다.

위치는 --config PATH → $GORI_CONFIG → $GORI_HOME/settings.json 순으로 결정되므로, CA·프로젝트 DB·테마·워드리스트를 옮기지 않고도 다른 설정으로 실행할 수 있습니다. 섹션 단위 이동은 gori settings export / import로 합니다. 그중 rewriter·scan_rules·decoder·statusline·editor 다섯 섹션은 명령을 담을 수 있어 프로필에 코드가 실릴 수 있습니다. 내보낼 때와 가져올 때 모두 그 사실을 알려줍니다.

network

{
  "network": {
    "bind_host": "127.0.0.1",
    "bind_port": 8070,
    "upstream_proxy": ""
  }
}
Key Type Default Description
bind_host string 127.0.0.1 전역 기본 리스닝 주소 (프로젝트에 net.bind_host가 없을 때 사용)
bind_port integer 8070 전역 기본 리스닝 포트 (프로젝트에 net.bind_port가 없을 때 사용)
upstream_proxy string "" 전역 기본 업스트림: 기존 host:port/http://…, http+tls://…(프록시까지 TLS), 또는 socks5://…/socks5h://…; 비어 있으면 환경변수(HTTPS_PROXY / HTTP_PROXY / ALL_PROXY)를 먼저 확인한 뒤 직접 연결합니다. 설정 시 프로젝트 net.upstream_proxy가 우선. https://…는 평문 형식의 기존 표기입니다. upstream_rules 참고
upstream_proxy_ca string "" http+tls 홉에서 업스트림 프록시의 인증서를 검증할 PEM 번들. 시스템 스토어에 더해서 신뢰합니다. 비우면 시스템 스토어만 사용. 비밀이 아니라 경로이므로 프로필로 공유해도 안전합니다
upstream_proxy_insecure bool false 업스트림 프록시 인증서 검증을 건너뜁니다. origin을 다루는 verify_upstream이나 --insecure-upstream과는 무관하며 그 플래그에 영향받지 않습니다. 이 홉은 모든 CONNECT authority와 모든 Proxy-Authorization 자격증명을 실어 나르므로 기본값은 꺼짐입니다
verify_upstream bool true 시스템 CA 트러스트 스토어로 업스트림 TLS 인증서 검증(표준 위치에서 자동 탐색하며 SSL_CERT_FILE / SSL_CERT_DIR 반영). 스토어를 못 찾으면 SSL_CERT_FILE을 지정하거나 이 설정을 끌 때까지 HTTPS 검증이 실패합니다. 토글하면 재시작 없이 실행 중인 프록시, 액티브 프로브, Repeater / Fuzzer / Miner 전송기에 즉시 반영됩니다. --insecure-upstream은 해당 세션에만 끈 상태로 시작
serve_landing bool true 내장 안내 / CA 다운로드 페이지 제공. 리슨 주소로 직접 접속한 경우와, 이미 프록시를 설정한 클라이언트가 예약 호스트 http://gori.proxy/(또는 http://gori/)로 접속한 경우 모두 해당
connect_timeout_secs integer 30 업스트림 연결 타임아웃(초, 최소 1)
io_timeout_secs integer 30 업스트림 읽기 / 쓰기 유휴 타임아웃(초, 최소 1)
capture_max_mib integer 2 메시지당 저장하는 본문의 최대 크기(MiB, 1-2047). 더 큰 본문도 바이트 그대로 전달되며, 잘리는 것은 저장본뿐이고 실제 전송 크기는 기록됩니다
http2 string "auto" auto는 원 서버의 ALPN을 반영하고, off는 모든 터널 연결을 HTTP/1.1로 강제합니다. 아래 http2를 참고하세요
strip_alt_svc bool false HTTP/3을 광고하는 Alt-Svc 응답 필드를 클라이언트에 도달하기 전에 제거하므로, 브라우저가 gori가 나르지 않는 전송으로 넘어갈 수 없습니다. 아래 strip_alt_svc를 참고하세요
strip_extended_connect bool false 원 서버의 HTTP/2 SETTINGS_ENABLE_CONNECT_PROTOCOL을 클라이언트에 넘기지 않으므로, 브라우저가 메시지 단위 인터셉트와 Match & Replace가 동작하는 HTTP/1.1 Upgrade로 WebSocket을 엽니다. 아래 strip_extended_connect를 참고하세요
strip_available_dictionary bool false 요청이 원 서버에 닿기 전에 Available-Dictionary와 Dictionary-ID를 제거하므로, 원 서버가 gori가 해독할 수 없는 dcb/dcz 본문으로 응답하지 못합니다. 아래 strip_available_dictionary를 참고하세요
tls_passthrough array [] 복호화하지 않고 중계할 호스트 목록. 아래 tls_passthrough를 참고하세요

CLI --listen / --port는 현재 프로세스에서만 이 값을 오버라이드합니다(디스크에 기록되지 않음). 프로젝트별 오버라이드를 참고하세요.

http2

auto(기본값)는 원 서버의 ALPN을 반영합니다. 원 서버가 HTTP/2를 지원할 때만 클라이언트에 h2를 광고합니다. off는 광고하지 않으므로 모든 터널 연결이 HTTP/1.1 경로를 탑니다.

h1과 h2의 차이(요청 프레이밍, 헤더 이름 처리, 스머글링)를 시험할 때 버전을 고정하세요.

이 설정이 생기기 전에는 Match & Replace 규칙이 활성일 때 gori가 HTTP/1.1로 내려갔으므로, h1을 강제하려면 아무 동작도 하지 않는 규칙을 켜야 했습니다. 그러면 헤드 재작성도 함께 켜지고, 켜둔 것을 잊기도 쉬웠습니다.

off는 다음 터널 연결부터 적용되며, 원 서버 ALPN 프로브를 생략합니다(원 서버당 연결 1개 절약). 이제 규칙 때문에 연결이 내려가는 일은 없습니다. 인터셉트, Match & Replace 규칙(헤드, 바디, short circuit), 세션 바인딩 extract 규칙, Sandbox 모두 HTTP/2 릴레이에서 동작합니다. 클라이언트가 preface를 보내며 이미 h2를 확정했으므로, CONNECT 안의 평문 HTTP/2(h2c) 터널은 off일 때 거부합니다.

다운그레이드는 모두 gori.log에 호스트당 한 번, 호스트 이름과 원인이 된 이유와 함께 기록됩니다. 다운그레이드가 적용되는 동안 HTTP/2 전용 클라이언트(모든 gRPC 클라이언트)는 그 호스트에 연결할 수 없고, 그 이유가 적히는 곳은 이 로그 줄뿐입니다.

원 서버가 HTTP/2를 지원하지 않을 때의 폴백을 정의해야 하므로 force 모드는 없습니다.

tls_passthrough

호스트가 일치하는 CONNECT는 200으로 응답한 뒤 불투명한 바이트 터널로 중계됩니다. 해당 호스트용 인증서를 발급하지 않고, 복호화하지 않으며, 아무것도 캡처하지 않습니다. 클라이언트는 gori가 경로에 없을 때처럼 원 서버의 인증서를 직접 검증합니다.

인증서를 피닝하는 클라이언트(모바일 앱, 자동 업데이터, 데스크톱 에이전트)가 대상과 프록시를 공유할 때 쓰세요. 이 설정이 없으면 그 트래픽은 깨집니다. 스코프로는 해결되지 않습니다. 스코프는 무엇을 기록하고 개입할지를 정할 뿐 TLS를 가로챌지는 정하지 않으므로, 스코프 밖 호스트도 복호화됩니다.

같은 경로 위의 비-HTTP 프로토콜(MQTT, AMQP, 데이터베이스 와이어 프로토콜 등 첫 바이트가 텍스트가 아닌 것)에도 씁니다. passthrough가 없으면 gori는 그런 연결의 TLS를 종료한 뒤 HTTP 요청이 아닌 바이트를 받습니다. 이 연결은 관찰한 바이트를 담은 not an HTTP request 플로우로 기록됩니다. 여기에 호스트를 추가하면 gori는 바이트 그대로 터널링합니다.

텍스트 줄로 시작하는 프로토콜(SSH의 SSH-2.0-… 배너, SMTP 인사말)은 감지하지 않습니다. 첫 줄이 malformed 요청 라인처럼 보이고, gori는 그런 요청 라인을 바이트 그대로 전달하기 때문입니다. 그런 연결은 head 타임아웃을 기다립니다. 이 경우에도 passthrough를 쓰세요.

판단할 바이트가 없는 두 가지 경우에도 이 설정을 씁니다. 서버가 먼저 말하는 프로토콜(SMTP, IMAP, POP3, MySQL)은 클라이언트가 접속만 하고 아무것도 보내지 않으므로 분류할 대상이 없습니다. 읽기가 타임아웃되면 그 형태를 밝힌 no request 플로우로 기록됩니다. 리버스·트랜스페어런트 리스너에서는 그 플로우에 클라이언트가 향하던 원 서버가 적힙니다. 리버스는 선언된 원 서버이고, 트랜스페어런트는 플랫폼이 답해 줄 때 커널 리다이렉트에서 읽은 원 서버입니다. 리다이렉트된 :25나 :143이라면 그 이름이 여기에 등록할 호스트입니다. socks5 리스너에서는 핸드셰이크가 거기까지 진행됐다면 클라이언트가 요청한 목적지가 적힙니다. 그 전이라면 적을 이름이 없습니다. 포워드 프록시 리스너에는 이름을 실어 올 바이트가 도착하지 않으므로, 플로우에는 해당 포트에서 gori를 빼라는 안내가 남습니다.

CONNECT 안의 비-TLS 페이로드(ssh -o ProxyCommand='nc -X connect proxy:8080 %h %p', 흔한 사내 프록시 패턴)는 시작 바이트를 밝힌 플로우를 남기고 거부됩니다. 호스트를 등록하면 동작합니다. 등록된 호스트는 어떤 프로토콜인지 엿보지 않고 바이트 그대로 중계됩니다. 같은 peek이 h2c 터널을 첫 바이트가 아닌 PRI * HTTP/2.0 프리페이스 전체로 식별하므로, 80 포트로 터널링한 평문 POST나 PROPFIND는 다른 해독 불가 페이로드처럼 거부됩니다.

터널링된 원 서버로 향하는 클라이언트와 gori가 TLS 핸드셰이크를 완료하지 못하면(대개 클라이언트가 아직 CA를 신뢰하지 않아서, 인증서를 피닝하는 클라이언트라면 항상) 호스트·포트·사유별로 한 번씩 gori.log에 남깁니다. 클라이언트가 CA를 신뢰하기 전에 오는 gori.proxy의 CA 다운로드 페이지는 제외합니다.

{
  "network": {
    "tls_passthrough": ["updates.example.com", "*.push.apple.com"]
  }
}

패턴은 스코프 host 룰과 같은 문법입니다. example.com은 해당 호스트와 그 서브도메인까지 포함하고, *.push.example.com은 글롭(서브도메인만, 맨 호스트는 제외)이며, IPv6 리터럴은 대괄호 유무와 무관하게 일치합니다. 대소문자를 구분하지 않습니다. 항목은 호스트만 적습니다. 스킴, 경로, :port가 붙은 항목은 어떤 것과도 일치할 수 없으므로 저장할 때 거부됩니다.

비어 있으면(기본값) 모두 가로챕니다. 평문 HTTP는 영향을 받지 않습니다.

우회된 호스트는 플로우를 남기지 않으므로, gori는 호스트별로 처음 중계할 때 로그에 한 줄을 남깁니다. 목록은 Preferences → Network & Tabs → Network → TLS passthrough에서 쉼표로 구분해 편집합니다.

strip_alt_svc

QUIC은 UDP이고 gori의 리스너는 전부 TCP 소켓이므로 gori는 HTTP/3을 가로채지 않습니다. 원 서버가 Alt-Svc: h3=":443"으로 응답하면 클라이언트가 gori가 읽을 수 없는 전송으로 넘어갈 수 있고, 그때부터 History가 끊깁니다. 이 설정을 켜면 gori는 h3(또는 h3-… 드래프트)을 광고하는 Alt-Svc 필드를 클라이언트가 받는 응답에서 제거합니다. HTTP/1.1과 HTTP/2 양쪽에 적용됩니다.

기본값은 꺼짐입니다. gori는 그대로 두면 캡처가 틀어지는 경우에만 사용자 지시 없이 응답을 편집합니다. Sec-WebSocket-Extensions 제거가 그 경우입니다. permessage-deflate가 협상되면 저장된 모든 프레임이 페이로드로 보이는 deflate 스트림이 됩니다. 그대로 둔 Alt-Svc는 gori가 기록하는 어떤 것도 망가뜨리지 않고 클라이언트가 떠나게 할 뿐이므로, 제거 여부는 시험에 따라 정하세요.

꺼 두면, 대신 그 사실을 알립니다. h3를 광고하는 응답이 제거되지 않은 채 클라이언트에 도달하면 그 플로우에 증거와 설정을 함께 밝히는 안내가 남습니다: "kept 1 Alt-Svc HTTP/3 advertisement (h3=":443") in this response — gori does not intercept HTTP/3, so a client acting on it leaves the proxy and what it does there is missing from History (settings network.strip_alt_svc is off)." HTTP/1.1과 HTTP/2 양쪽에서, 제거 안내가 뜨는 자리에 뜹니다. 와이어 위의 바이트는 바뀌지 않습니다. 원 서버의 헤드는 바이트 그대로 클라이언트에 도달합니다. 호스트당 한 번씩 gori.log에도 한 줄이 남고, 패시브 프로브의 tech_http3 핑거프린트도 호스트당 한 번 Alt-Svc: <host> advertised HTTP/3 이벤트를 올립니다(Probe 탭으로 바로 이동 가능). 이 안내는 플로우 단위 기록을 더합니다.

제거는 필드 단위이고, h3를 광고하는 필드에만 적용됩니다. Alt-Svc: clear는 제거하지 않습니다. RFC 7838 §3에서 이 값은 캐시된 대체 경로를 잊으라는 지시이기 때문입니다. 일반 h2=":8443" 대체 경로도 제거하지 않습니다. 다른 TCP 포트일 뿐이어서 계속 gori를 거쳐 터널링됩니다.

제거는 Match & Replace보다 먼저 실행되므로, 헤더를 도로 넣는 응답 head 규칙이 우선합니다.

HTTP/2에서 필드를 하나 제거하면 gori는 그 응답의 헤더 블록을 다시 인코딩합니다. HPACK 상태는 연결 단위이므로 이 전환은 되돌릴 수 없습니다. 처음 제거한 시점부터 gori는 그 연결의 모든 응답 헤드를 다시 인코딩하며, 그 연결에서는 원 서버의 HPACK 압축을 포기합니다. 그 시점부터 해당 연결의 raw 프레임 로그에는 gori의 HPACK이 남고, 플로우의 안내가 그 사실을 밝힙니다. 트레일러 블록과 PUSH_PROMISE는 건드리지 않습니다. 둘 중 어디에 있는 Alt-Svc도 클라이언트가 따르지 않기 때문입니다.

응답에서 필드를 제거한 플로우에는 무엇을 지웠는지 밝히고 지운 값을 인용한 안내가 남습니다. History 상세 패널, gori run history --format json, MCP get_flow 도구에서 볼 수 있습니다. 패시브 프로브는 저장된 응답, 곧 gori가 전달한 응답을 읽으므로, 제거를 켜고 나면 캡처된 플로우에서는 tech_http3 핑거프린트와 그 Alt-Svc: <host> advertised HTTP/3 이벤트 줄이 뜨지 않습니다. 그 사실은 플로우별 안내에 기록됩니다. 영향을 받는 것은 캡처된 트래픽뿐입니다. gori가 직접 보낸 요청의 응답(Repeater 전송, Fuzz 스윕, Discover 크롤, MCP send_request, import)은 프록시 경로를 지나지 않으므로 원 서버의 Alt-Svc가 남고 핑거프린트도 뜹니다. 광고를 보려면 Repeater로 다시 보내세요.

메울 수 없는 것이 셋 있습니다. tls_passthrough에 등록된 호스트는 복호화되지 않으므로 gori가 편집할 응답이 없습니다. 클라이언트는 DNS HTTPS 레코드로도 h3 경로를 알아낼 수 있고, 응답 쪽 제거로는 이를 막지 못합니다. 콜론 앞에 공백이 있는 필드명(Alt-Svc : h3=…)은 이 설정도, gori의 헤더 투영도 인식하지 않습니다. 규격을 지키는 클라이언트도 그 필드는 거부합니다(RFC 9112 §5.1). 이 설정은 Preferences → Network & Tabs → Network → Strip HTTP/3 Alt-Svc에서 켜고 끕니다.

strip_extended_connect

원 서버가 SETTINGS_ENABLE_CONNECT_PROTOCOL(RFC 8441)을 제안하면 브라우저는 WebSocket을 HTTP/2 위에서 엽니다. gori는 그런 소켓도 빠짐없이 캡처하지만, 메시지 단위 인터셉트와 Match & Replace는 그 위에서 동작하지 않습니다. 이 설정을 켜면 gori는 HTTP/2 연결에서 원 서버가 보내는 모든 SETTINGS 프레임에서 그 파라미터를 지운 뒤 클라이언트에 넘깁니다. 확장 CONNECT를 제안받은 적 없는 클라이언트는 새 연결에서 HTTP/1.1 Upgrade로 WebSocket을 열고, 거기서는 둘 다 동작합니다. 그 연결의 나머지는 계속 HTTP/2입니다. TLS 터널, CONNECT 안의 h2c, 리버스·트랜스페어런트 리스너 모두에 적용됩니다.

기본값은 꺼짐입니다. 이유는 strip_alt_svc와 같습니다. HTTP/2 소켓이라고 캡처가 덜 정확해지지는 않으므로, 소켓을 옮길지는 시험에 따라 정하세요. http2를 off로 두어도 소켓은 HTTP/1.1로 옮겨 가지만, 연결 전체가 함께 옮겨 갑니다.

켠 뒤에 열린 연결부터 적용됩니다. 원 서버는 보통 첫 SETTINGS 프레임에서 이 파라미터를 한 번만 보내므로, 클라이언트가 이미 붙들고 있는 연결은 받은 제안을 유지하고, 이미 HTTP/2 위에서 돌고 있는 소켓도 그대로 남습니다. gori가 새 연결을 강제하려고 연결을 끊지는 않습니다. 설정이 켜진 동안 HTTP/2로 열린 WebSocket에는 설정이 그 소켓을 막지 못했다는 안내가 남습니다.

gori는 한 일을 밝힙니다. SETTINGS 프레임에는 플로우가 없으므로 기록은 세 곳에 남습니다. raw 프레임 로그에는 gori가 보낸, 파라미터가 빠진 프레임이 남습니다. gori.log에는 원 서버마다 한 번 이름이 적힙니다. 설정이 켜진 동안 그 원 서버로 가는 HTTP/1.1 WebSocket 업그레이드마다 다음 안내가 남습니다: "gori withheld <host>:<port>'s SETTINGS_ENABLE_CONNECT_PROTOCOL from the client on HTTP/2 (settings network.strip_extended_connect), so a client that would have opened this WebSocket there used the HTTP/1.1 Upgrade instead."

이 파라미터는 모든 확장 CONNECT 프로토콜이 함께 쓰는 비트 하나이므로, connect-udp(RFC 9298)와 connect-ip(RFC 9484)도 함께 막힙니다. 값이 0인 항목은 아무것도 바꾸지 않으므로 그대로 둡니다. 그래도 확장 CONNECT를 보내는 클라이언트는 거부하지 않고 중계합니다. 영향을 받는 것은 프록시 경로뿐입니다. Repeater나 Fuzzer의 재전송은 원 서버에 직접 접속하므로 여전히 제안을 받습니다. 이 설정은 Preferences → Network & Tabs → Network → Strip HTTP/2 ext. CONNECT에서 켜고 끕니다.

strip_available_dictionary

Compression Dictionary Transport(RFC 9842)에서 클라이언트는 자신이 가진 사전을 Available-Dictionary(사전의 SHA-256)와 Dictionary-ID로 원 서버에 알립니다. 그러면 원 서버는 Content-Encoding: dcb(Brotli)나 dcz(Zstandard)로 응답할 수 있는데, 이 본문은 그 사전으로만 풀립니다. 사전은 클라이언트가 앞서 캐시한 응답이고, gori가 경로에 들어오기 전에 받은 것인 경우가 많습니다.

이 설정이 꺼져 있으면 본문은 바이트 그대로 캡처되지만 내용은 읽을 수 없습니다. 상세 뷰, 패시브 프로브 규칙, extract 규칙, Match & Replace 본문 규칙이 모두 압축된 바이트를 보며, 디코드 안내는 *"compressed: dcb — unsupported without the client's dictionary (RFC 9842); settings network.strip_available_dictionary"*로 나옵니다.

켜면 gori는 HTTP/1.1과 HTTP/2 모두에서 요청이 원 서버로 나가기 전에 Available-Dictionary와 Dictionary-ID 필드를 모두 제거합니다. 사전의 해시가 없으면 원 서버는 dcb나 dcz를 만들 수 없으므로 gori가 해독하는 코딩으로 응답합니다. Accept-Encoding은 클라이언트가 보낸 그대로 둡니다. 해시가 사라지면 그 안의 dcb/dcz 토큰은 아무 효과가 없고, gori는 필드의 일부를 고쳐 쓰지 않고 필드 전체를 지웁니다. History에는 gori가 보낸 요청이 기록됩니다.

기본값은 꺼짐입니다. 이유는 strip_alt_svc와 같습니다. 읽을 수 없는 본문이라도 gori가 기록하는 것을 망가뜨리지는 않고, 디코드 안내가 이유를 밝힙니다. 켜면 클라이언트가 gori를 거치는 동안 사전으로 아끼던 만큼 원 서버의 응답이 커집니다.

제거는 Match & Replace보다 먼저 실행되므로, 특정 호스트에서 요청 head 규칙으로 필드를 되돌려 놓으면 그 규칙이 우선하고, 플로우에는 그 필드를 제거했다는 안내가 남지 않습니다.

HTTP/2에서 필드를 하나 제거하면 gori는 그 요청의 헤더 블록을 다시 인코딩합니다. HPACK 상태는 연결 단위이므로 이 전환은 되돌릴 수 없습니다. 처음 제거한 시점부터 gori는 그 연결의 모든 요청 헤드를 다시 인코딩하고, 그 방향에서 클라이언트의 HPACK 압축을 포기합니다. raw 프레임 로그에도 gori의 HPACK이 남습니다. 트레일러 블록은 건드리지 않습니다.

gori는 한 일을 밝힙니다. 요청에서 필드를 제거한 플로우마다 다음 안내가 남습니다: "removed 2 dictionary fields (Available-Dictionary: :…:, Dictionary-ID: "…") from this request — a response compressed against a dictionary gori does not hold (RFC 9842 dcb/dcz) cannot be decoded (settings network.strip_available_dictionary)." HTTP/2에서는 그 연결의 요청 헤드를 이후 다시 인코딩한다는 문장이 덧붙고, gori.log에는 연결마다 첫 제거가 한 번 적힙니다.

영향을 받는 것은 프록시 경로뿐입니다. Repeater, Fuzzer, Miner의 전송은 운영자의 바이트를 그대로 보내므로, 그 필드를 담은 캡처 요청을 재전송하면 여전히 dcb 응답을 받을 수 있고, 그 디코드 안내가 이유를 밝힙니다. 이 설정은 Preferences → Network & Tabs → Network → Strip dictionary offer에서 켜고 끕니다.

listeners

기본 network.bind_host / bind_port 외에 프록시가 추가로 수신할 소켓입니다.

{
  "listeners": [
    { "host": "192.168.1.10", "port": 8081, "mode": "proxy" },
    { "host": "127.0.0.1", "port": 8080, "mode": "transparent", "target_port": 80 },
    { "host": "127.0.0.1", "port": 8443, "mode": "transparent", "target_port": 443 },
    { "host": "0.0.0.0", "port": 9000, "mode": "reverse", "origin": "https://api.example.com" },
    { "host": "127.0.0.1", "port": 1080, "mode": "socks5" }
  ]
}
Key Type Default Description
host string — 수신 주소. 필수
port integer — 수신 포트. 필수
mode string "proxy" proxy, transparent, reverse, socks5 중 하나. 알 수 없는 모드는 항목을 버립니다(proxy로 기본 처리하면 LAN 주소에 의도치 않은 포워드 프록시를 노출할 수 있으므로)
target_port integer 80 / 443 transparent 전용. 클라이언트가 어느 포트로 접속했는지 커널이 알려주지 못할 때 쓸 업스트림 포트. 권고값입니다. 투명 모드 참고
origin string — reverse 전용, 필수. 전달할 절대 http(s) URL
rewrite_host boolean false reverse 전용. 전달되는 Host를 origin의 authority로 교체

모드에 맞지 않는 필드는 무시하지 않고 거부합니다. transparent가 아닌 항목의 target_port, reverse가 아닌 항목의 origin 또는 rewrite_host가 여기에 해당합니다. 그래서 socks5 항목은 host, port, mode만 갖습니다.

기본 bind는 스칼라로 남습니다. 클라이언트에 설정하는 포워드 프록시 엔드포인트이고, 상태바, statusline JSON, capture-status 사이드카, 라이브 rebind가 보고하는 대상도 이것입니다. 추가 리스너는 인벤토리로 보여 줍니다. 하나라도 설정되어 있으면 listen 칩 옆에 listeners:N 칩이 나타나고, 모드 · 주소 · origin · 상태를 담은 읽기 전용 목록을 엽니다. 하나라도 떠 있지 않으면 칩이 listeners:N/M으로 바뀌며 빨갛게 표시됩니다.

기본 bind는 gori가 옮길 수 있으므로(포트가 사용 중이면 다음 포트로 넘어갑니다) 알려 줍니다. listeners의 주소는 전부 사용자가 적은 것이므로 목록은 확인만 해 줍니다.

추가 리스너가 바인드에 실패해도(특권 포트, 주소 사용 중) 기본 리스너의 캡처는 멈추지 않습니다. 실패는 listeners:N/M 칩에 드러나고 목록에 이유가 표시됩니다. 다른 이유로 사용할 수 없는 항목(origin 누락, 모드에 맞지 않는 필드)도 실행 집합에서 빠지고 같은 목록에 표시됩니다. 기본 주소와 중복되는 항목은 건너뜁니다.

이 섹션은 시작할 때 읽고 라이브로 반영하지 않습니다. 편집한 뒤 저장하면 재시작이 필요하다는 알림이 뜹니다.

투명 모드

투명 리스너는 자신이 원 서버와 통신한다고 믿는 클라이언트를 상대합니다. CONNECT도 절대 경로 대상도 없으므로 gori는 연결마다 두 출처에서 목적지를 복구합니다.

커널은 리다이렉트 규칙이 목적지를 바꾸기 전에 클라이언트가 어디로 접속했는지를 기억하고 있고, gori는 연결마다 한 번 커널에 묻습니다.

  • Linux: getsockopt(SOL_IP, SO_ORIGINAL_DST), v6 연결이면 SOL_IPV6 형태. 항상 사용할 수 있으며, 리다이렉트로 들어온 연결이 아니면 답이 없습니다.
  • macOS: /dev/pf에 대한 DIOCNATLOOK. 이 디바이스는 root 전용이라 gori가 root로 실행될 때만 동작합니다.

이 답은 주소와 포트입니다. 포트는 클라이언트가 연결한 포트이므로 target_port보다도, 클라이언트의 Host 헤더에 적힌 포트보다도 우선합니다. 주소는 클라이언트가 목적지를 뭐라고 불렀든 gori가 접속하는 곳입니다.

클라이언트가 보낸 바이트는 이름을 제공합니다. 평문은 Host 헤더, HTTPS는 핸드셰이크 이전에 ClientHello에서 읽는 TLS SNI입니다. 이름이 있으면 gori는 이름을 씁니다. 발급할 leaf 인증서, 샌드박스 게이트, passthrough 목록, 원 서버 ALPN 프로브, 스코프 매칭, History에 보이는 값에 모두 이름이 쓰입니다. 커널의 주소가 이름 자리에 들어가는 것은 이름이 없을 때뿐입니다.

이름은 목적지를 식별하고 업스트림으로 바이트 그대로 전달됩니다. 주소는 어느 기계에 연결될지를 정합니다. Host로 거짓말하는 클라이언트도 자기가 요청한 이름의 인증서를 받고 History에도 그 이름으로 남지만, gori의 업스트림 연결을 옮기지는 못합니다.

호스트명 오버라이드는 이름으로 적어 둔 매핑이므로 커널 주소보다 우선합니다. 투명 모드의 목적지를 다른 곳으로 돌리는 방법은 이것 하나뿐입니다.

어느 쪽이 목적지를 정했는지는 리스너마다 한 번, 이후 바뀌면 다시 한 번 로그에 남습니다.

방화벽으로 트래픽을 이 리스너에 보내세요. Linux:

iptables -t nat -A OUTPUT -p tcp --dport 80  -j REDIRECT --to-port 8080
iptables -t nat -A OUTPUT -p tcp --dport 443 -j REDIRECT --to-port 8443

macOS는 pf의 rdr 규칙을 사용합니다.

이 규칙은 TCP만 잡고, HTTP/3은 UDP입니다. HTTP/3을 쓰는 클라이언트는 UDP 443 포트로 QUIC을 보냅니다. 위 규칙은 QUIC을 리다이렉트하지 않고 gori 리스너도 읽지 못하므로, 그 요청은 원 서버에 그대로 도달하고 History에는 나타나지 않습니다. 같은 트래픽의 UDP 443을 거부하면 클라이언트가 TCP로 되돌아옵니다:

iptables -A OUTPUT -p udp --dport 443 -j REJECT

macOS에서는 pf에 block return out proto udp from any to any port 443을 넣습니다. strip_alt_svc는 HTTP/3을 광고하는 헤더를 제거합니다. 이 규칙은 캐시된 Alt-Svc나 DNS HTTPS 레코드로 이미 경로를 알고 있는 클라이언트까지 막습니다.

target_port가 아직 있는 이유. 커널 조회가 항상 답하지는 않습니다. Linux와 macOS 외에는 수단이 없고, macOS는 root가 필요하며, 리다이렉트 없이 리스너에 직접 들어온 연결은 복구할 이전 목적지가 없습니다. target_port는 그런 경우의 폴백입니다. 리다이렉트 규칙이 잡는 포트를 지정하므로, 리다이렉트된 :443 트래픽을 받는 리스너는 target_port: 443을 지정합니다. 커널이 답한 경우에는 이 값을 보지 않습니다.

커널이 답하지 않을 때. 이름을 DNS로 해석하므로 Host로 거짓말하는(또는 오해를 부르는 SNI를 보내는) 클라이언트가 업스트림 dial을 원하는 호스트로 돌릴 수 있고, 포트는 target_port가 정합니다. 수단이 없는 플랫폼, root가 아닌 macOS, 리다이렉트 없이 리스너에 직접 들어온 연결이 여기에 해당합니다. 어느 출처가 정했는지는 로그에 남습니다. 클라이언트가 목적지에 영향을 주면 안 된다면 reverse 모드를 쓰세요. 목적지를 선언하고 클라이언트가 보낸 것은 아무것도 보지 않으며, 플랫폼도 root도 가리지 않습니다.

그 밖의 동작은 프록시 경로와 같습니다. 플로우는 같은 프로젝트에 캡처되고, 스코프와 샌드박스가 적용되며, passthrough 목록도 지켜집니다. SNI 없는 TLS 연결은 커널이 주소를 알려주면 처리됩니다(gori가 그 IP로 leaf를 발급합니다). 주소도 없을 때만 끊고 한 번 로그를 남깁니다. TLS 클라이언트에게는 403으로 답할 수 없으므로 샌드박스가 배제한 호스트는 바로 끊습니다.

리버스 모드

리버스 리스너도 자신이 원 서버와 통신한다고 믿는 클라이언트를 상대하지만, 원 서버를 추론하지 않고 설정에 선언합니다. gori가 원 서버인 것처럼 응답하고 origin으로 전달합니다.

{ "host": "0.0.0.0", "port": 9000, "mode": "reverse", "origin": "https://api.example.com" }

프록시 설정이 없는 모바일 앱, CI 단계, 어플라이언스처럼 프록시를 지정할 수 없는 클라이언트에 쓰세요. CONNECT, 프록시 설정, 방화벽 규칙이 필요 없습니다. 클라이언트가 이 소켓에 닿기만 하면 됩니다.

목적지가 설정되어 있으므로 투명 모드의 실패 모드가 적용되지 않습니다. Host 헤더가 없는 요청도 처리합니다. 다른 곳을 가리키는 Host가 와도 처리하고, 그대로 origin으로 전달합니다. 라우팅에 그 헤더를 보지 않습니다.

origin은 http 또는 https 스킴의 절대 URL이어야 합니다. 포트 기본값은 스킴을 따릅니다. api.example.com:8443 같은 형태는 http로 가정하지 않고 거부합니다. 스킴이 gori가 원 서버와 TLS로 말할지를 정하기 때문입니다. gori의 기본 bind나 다른 리스너를 가리키는 origin은 전달 루프가 되므로 저장 시점에 거부합니다.

TLS. 클라이언트가 TLS로 열면 리스너가 종단하며, 클라이언트의 SNI가 아닌 설정된 origin 호스트 이름으로 leaf 인증서를 발급합니다. 따라서 클라이언트는 origin의 이름으로 이 소켓에 닿아야 하고, 이는 통상적인 리버스 프록시 구성입니다(hosts 항목이나 DNS 레코드). 원 서버 쪽 연결은 origin의 스킴을 따르므로 "origin": "http://127.0.0.1:3000"이면 평문 백엔드 앞에 TLS를 세우게 됩니다.

rewrite_host. 통상적인 리버스 프록시는 Host를 업스트림 이름으로 바꿉니다. 라이브 경로에서 클라이언트가 보낸 바이트를 바꾸는 일이므로 gori는 켰을 때만 그렇게 합니다. rewrite_host: false(기본값)이면 클라이언트의 Host가 바이트 그대로 원 서버에 도착합니다. 켜면 Host가 origin의 authority로 교체되고, 나머지 헤드는 그대로이며 중복된 Host는 하나로 합쳐집니다.

스코프는 다른 곳과 같습니다. 샌드박스와 exclude 룰은 그대로 적용되고, 요청마다 그리고 TLS 핸드셰이크 전에 검사합니다. include 목록은 여기서 게이트가 아니라 캡처된 트래픽을 보는 렌즈입니다. 리버스 리스너는 클라이언트가 보낸 것을 전달할 뿐이기 때문입니다.

SOCKS5 모드

SOCKS5 리스너(RFC 1928)는 목적지를 핸드셰이크에서 클라이언트로부터 받고, 그 뒤에 오는 것을 전부 가로챕니다. TLS든, HTTP/2 prior knowledge든, 평문 HTTP든, 다른 리스너와 마찬가지로 첫 바이트를 보고 갈라서 처리합니다. 여기서는 TLS 판정을 두 바이트로 하므로, 첫 옥텟이 우연히 0x16인 페이로드가 TLS 핸드셰이크로 넘어가지 않습니다. SOCKS 리스너에는 HTTP가 아닌 프로토콜이 도착할 가능성이 가장 큽니다. 대부분 ssh -D를 여기에 붙입니다.

{ "host": "127.0.0.1", "port": 1080, "mode": "socks5" }

ALL_PROXY=socks5://127.0.0.1:1080, 프록시 설정이 SOCKS뿐인 런타임, SOCKS만 할 줄 아는 도구처럼 SOCKS 프록시는 지정할 수 있지만 HTTP 프록시는 지정할 수 없는 클라이언트에 쓰세요. 이 리스너는 들어오는 방향입니다. "kind": "socks5"인 upstream_rules 항목은 반대 방향으로, 남의 SOCKS 프록시를 거쳐서 원 서버에 닿습니다.

목적지가 핸드셰이크에서 선언되어 도착하므로 커널 리다이렉트 규칙이 필요 없고, SNI나 Host 헤더에서 목적지를 복구할 일도 없습니다. 평문 연결에서는 Host가 다른 곳을 가리키는 요청도 핸드셰이크가 말한 곳으로 나가고, History가 기록하는 authority도 핸드셰이크 쪽이며, 클라이언트의 헤더는 바이트 그대로 전달됩니다. TLS 연결에서는 이름을 SNI가 대신 공급합니다. leaf 인증서가 그 이름으로 발급되고, passthrough 목록과 샌드박스도 그 이름으로 매칭하며, History에 보이는 것도 그 이름입니다. 연결은 핸드셰이크가 선언한 목적지로 dial 합니다. 투명 모드가 이름과 주소를 나누는 것과 같은 구분입니다. SNI가 없는 ClientHello라면 두 가지 모두 선언된 목적지를 씁니다.

NO-AUTH 전용. gori가 지원하는 방식을 하나도 제시하지 않은 클라이언트에게는 RFC 1928의 0xFF로 알리고 연결을 닫습니다. 옆에 있는 포워드 프록시 리스너에도 인증이 없습니다.

CONNECT 전용. BIND와 UDP ASSOCIATE는 그냥 끊지 않고 응답 코드 0x07로 거부하므로, 클라이언트가 실제 원인을 보고할 수 있습니다. BIND는 클라이언트를 대신해 소켓을 열어야 하고 UDP ASSOCIATE는 데이터그램 릴레이입니다. gori의 리스너는 전부 TCP 소켓입니다. HTTP/3에 손이 닿지 않는 것과 같은 이유입니다.

gori가 succeeded로 답하기 전에 두 가지를 검사하고, 각각 연결을 끊는 대신 응답 코드 0x02("not allowed by ruleset")로 거부합니다. gori가 서빙 중인 소켓을 가리키는 목적지(이 리스너든, 형제 리스너든, 기본 bind든 이 프록시가 자기 자신을 거쳐 dial 하게 됩니다)와 샌드박스가 배제하는 호스트입니다. 포워드 프록시의 CONNECT 경로에도 두 게이트가 있습니다. 거기서도 클라이언트가 목적지를 지목하기 때문입니다. 투명 리스너는 커널이 먼저 정하고, 그 답이 없을 때만 클라이언트가 말한 쪽을 씁니다.

모든 거부는 이유를 담은 플로우로 프로젝트에 기록되므로, 잘못된 포트를 가리킨 클라이언트, UDP를 요청한 클라이언트, SOCKS가 아닌 것으로 연결을 연 클라이언트도 History에 나타납니다.

upstream_rules

network.upstream_proxy는 catch-all 경로입니다. host:port와 http://…는 평문 HTTP CONNECT 프록시를 사용합니다(기본 포트 8080). http+tls://…는 같은 CONNECT 프로토콜을 쓰지만 프록시까지의 홉을 TLS로 감쌉니다(기본 포트 443). socks5://…는 대상 이름을 로컬에서 해석해 주소 리터럴을 보내고, socks5h://…는 호스트 이름을 ATYP DOMAIN으로 보내 프록시가 해석합니다. 두 SOCKS 형식 모두 기본 포트는 1080입니다. URI 자격증명은 거부됩니다. Project 탭에서 직접 자격증명을 설정하거나 username과 password_env가 있는 upstream_rules 항목을 사용하세요.

이 스칼라가 비어 있으면 gori는 dial 시점에 프로세스 환경을 확인합니다. HTTP origin은 HTTP_PROXY, ALL_PROXY 순서로, HTTPS origin은 HTTPS_PROXY, HTTP_PROXY, ALL_PROXY 순서로 선택합니다. 대문자 이름을 우선하고 소문자 표기도 지원합니다. NO_PROXY / no_proxy는 *, 호스트·도메인, 대괄호로 감싼 IPv6 리터럴, 선택적인 포트, IPv4/IPv6 CIDR 블록(10.0.0.0/8,fd00::/8, 주소 리터럴 목적지와 대조)을 지원합니다. 일치하면 직접 연결합니다. localhost와 루프백 주소는 NO_PROXY와 무관하게 항상 직접 연결합니다. TLS passthrough와 CONNECT 터널을 포함한 모든 dial에서 그렇습니다. 이 예외는 목적지 기준이므로 프록시 자체가 127.0.0.1에 있어도 원격 목적지에는 그 프록시를 씁니다. 미지정 주소 0.0.0.0과 ::도 여기서는 루프백으로 취급하며, 시스템 리졸버가 받아들이는 숫자 IPv4 표기(127.1, 0x7f.0.0.1, 2130706433)도 마찬가지입니다. 루프백 판정과 CIDR 항목은 이런 목적지를 리졸버가 해석하는 점 표기 주소로 읽고, dial과 CONNECT 라인은 보낸 표기를 그대로 유지합니다. gori 셸 안에서는 그 셸이 내보낸 프록시 변수(셸을 띄운 gori를 가리키는 값)를 건너뛰고, 셸이 대체한 원래 값(사내 HTTPS_PROXY와 그 NO_PROXY)을 대신 읽습니다. 그래서 그 안에서 시작한 gori가 부모 gori를 거쳐 요청을 이중으로 보내지 않습니다. 명시적인 프로젝트 업스트림, 일치하는 규칙(direct 포함), 비어 있지 않은 스칼라가 환경변수보다 우선합니다. 환경변수 convention에서 http://는 평문 HTTP CONNECT 프록시(포트를 생략하면 스칼라의 8080이 아니라 80), https://는 프록시까지 TLS를 의미합니다. 저장된 network.upstream_proxy의 https://는 기존의 평문 의미를 유지합니다.

https://는 TLS가 아니라 평문 프록시입니다

https://proxy:3128은 gori가 프록시에 TLS로 말할 수 있게 되기 전처럼 평문 HTTP CONNECT 프록시를 의미합니다. 기존 settings.json 파일이 그 뜻으로 쓰고 있으므로, gori는 이 표기를 바꾸지 않고 받아들이며 다음과 같이 알립니다.

  • 설정된 https:// 업스트림마다 시작 시 경고 한 줄을 출력하고, 두 가지 수정 방법을 모두 알려줍니다.
  • 동작은 같고 모호함만 없애려면 http://로, 프록시까지의 홉을 암호화하려면 http+tls://로 쓰세요.
  • settings:network(또는 Project settings 카드)에서 프록시 필드를 편집해 저장하면 값이 http://…로 정규화되어 기록됩니다. 건드리지 않은 값은 적힌 바이트 그대로 보존됩니다.

프록시까지 TLS (http+tls)

도달하려는 origin을 이름으로 적는 CONNECT 요청 라인과 Proxy-Authorization 헤더는 TLS 세션 안에서 전송됩니다. 핸드셰이크가 끝나기 전에는 요청의 어떤 부분도 전송되지 않습니다.

프록시 leg는 프록시 자신의 호스트 이름으로 검증됩니다. SNI와 인증서 이름 검증 대상은 설정한 프록시 주소이며, origin의 이름도 호스트 오버라이드도 아닙니다(오버라이드는 origin leg에만 적용됩니다). 이 정책은 network.upstream_proxy_ca와 network.upstream_proxy_insecure가 결정하며, origin을 설명하는 verify_upstream / --insecure-upstream이 아닙니다. origin 정책을 느슨하게 해도 gori는 프록시를 계속 인증하며, 프록시 인증서가 거부되면 --insecure-upstream을 권하지 않고 프록시 실패로 보고합니다.

http+tls 프록시를 거쳐 도달하는 https:// origin은 TLS 안의 TLS입니다. origin 핸드셰이크가 터널 위에서 수행되므로 origin 인증서는 여전히 origin의 정책에 따라 end-to-end로 검증됩니다.

캡처·재전송·스캔 엔진, 업데이트 확인, OAST 제공자 통신을 포함해 gori가 여는 모든 네트워크 연결은 이 라우팅 결정을 사용합니다. 설정된 프록시가 잘못되었거나 연결할 수 없거나 터널을 거부하면 직결로 재시도하지 않고 실패합니다. 빈 프로젝트 고정값과 일치하는 direct 규칙은 예외입니다.

목적지별 규칙은 "*.corp.internal은 사내 프록시로, 나머지는 직결"을 표현하고 자격증명을 실으며 서로 다른 프록시를 선택할 수 있습니다.

규칙은 순서가 있고 첫 일치가 우선합니다. 구체적인 규칙을 위에 두세요. gori settings --edit로 편집합니다.

{
  "upstream_rules": [
    { "host": "intranet.corp.internal", "kind": "direct" },
    {
      "host": "*.corp.internal",
      "kind": "http",
      "addr": "proxy.corp.internal:3128",
      "username": "alice",
      "password_env": "CORP_PROXY_PASS"
    },
    { "host": "*.partner.example", "kind": "http+tls", "addr": "proxy.partner.example:443" },
    { "host": "*.onion", "kind": "socks5h", "addr": "127.0.0.1:9050" }
  ]
}
Key Type Description
host string 호스트 패턴. 스코프 host 룰과 같은 문법. corp.internal은 해당 호스트와 서브도메인, *.corp.internal은 글롭, *는 catch-all. 대소문자 무관
kind string direct, http, http+tls(TLS 위의 HTTP CONNECT), socks5(로컬 DNS), socks5h(프록시 DNS). 알 수 없는 kind(또는 빠진 host)는 규칙을 버리고, 파일을 고칠 때까지 규칙으로 라우팅되는 모든 연결을 닫힌 상태로 실패시킵니다(direct로 취급하면 의도한 프록시를 조용히 비활성화하게 되므로)
addr string 프록시 host:port. 포트 기본값은 http가 8080, http+tls가 443, 두 SOCKS kind가 1080. direct에는 없어야 합니다
username string 선택. http와 http+tls는 HTTP Basic(RFC 7617), 두 SOCKS kind는 RFC 1929 교환으로 전송
password_env string 선택. 비밀번호를 담은 OS 환경변수의 이름

전역 규칙 비밀번호는 settings.json에 저장되지 않습니다. 사용자명과 환경변수 이름만 기록되고, 비밀번호는 dial 시점에 OS 환경에서 읽습니다. 따라서 export CORP_PROXY_PASS=…가 재시작 없이 반영됩니다. gori의 env 섹션은 쓰지 않습니다. 그 변수는 settings.json에 평문으로 저장되기 때문입니다(#439 참고). $가 포함된 password_env는 거부됩니다. 값이 아니라 변수 이름을 담는 필드입니다. Project settings에서 직접 입력한 자격증명의 저장 방식은 프로젝트별 오버라이드를 참고하세요.

network.upstream_proxy_ca와 network.upstream_proxy_insecure는 규칙에서 왔든, 스칼라에서 왔든, 프로젝트 고정값에서 왔든 모든 http+tls 홉에 공통으로 적용되는 정책입니다. 규칙별 TLS 필드는 없습니다.

스칼라와 규칙은 같은 DNS 구분을 사용합니다. socks5는 gori 호스트에서 대상 이름을 조회하고, socks5h는 프록시에 조회를 맡깁니다. Tor, 분할 DNS, 로컬에서 해석할 수 없는 이름을 아는 점프호스트에는 socks5h를 사용하세요. 로컬 조회가 실패하면 프록시에 연결하기 전에 중단되며 원 서버 직결로 폴백하지 않습니다.

우선순위(높은 것부터):

우선순위 출처
1 (최상) 프로젝트 net.upstream_proxy. 프로젝트별 고정값으로, 테이블 전체를 건너뜁니다
2 upstream_rules의 첫 호스트 일치
3 network.upstream_proxy. 암묵적 catch-all
4 스칼라가 비어 있을 때 프로세스 환경(HTTPS_PROXY / HTTP_PROXY / ALL_PROXY), NO_PROXY / no_proxy(호스트·도메인·포트·CIDR 블록) 적용; localhost와 루프백은 여기서 항상 직접 연결
5 (최하) 직접 연결

열려 있는 프로젝트에서는 Destination host가 이 테이블보다 먼저 평가됩니다. 기본값 *는 위 우선순위를 그대로 두고, 일치하지 않는 목적지는 전역 규칙이나 스칼라 프록시로 폴백하지 않고 직접 연결됩니다.

규칙은 호스트 오버라이드를 적용하기 전의 원래 호스트명으로 매칭합니다. 오버라이드는 어느 IP로 접속할지만 바꿉니다.

outbound_tls

gori가 거는 연결의 목적지별 TLS 정책입니다. 제시할 클라이언트 인증서, 협상할 프로토콜 범위와 암호군, gori가 보내는 ClientHello의 형태(TLS 지문)를 정합니다. 순서가 있고 첫 일치가 우선하며, 호스트 패턴 문법은 같습니다. gori settings --edit로 편집합니다.

upstream_rules와는 별도 테이블입니다. 둘 다 목적지 호스트로 키를 잡고 호스트당 첫 일치 한 행만 적용하므로, 테이블이 나뉘어 있어야 "전부 사내 프록시 경유 + 한 호스트만 클라이언트 인증서"를 그 호스트 행에 프록시 주소를 중복하지 않고 쓸 수 있습니다.

{
  "outbound_tls": [
    {
      "host": "mtls.example.com",
      "client_cert": "/home/you/certs/client.crt.pem",
      "client_key": "/home/you/certs/client.key.pem"
    },
    {
      "host": "legacy-appliance.internal",
      "min_version": "tls1.0",
      "ciphers": "ALL:@SECLEVEL=0",
      "permissive": true
    }
  ]
}
Key Type Description
host string 호스트 패턴. upstream_rules와 동일하며 *는 catch-all
client_cert string 제시할 PEM 인증서 체인 경로(상호 TLS)
client_key string 대응하는 PEM 개인키 경로. 둘 다 있어야 하거나 둘 다 없어야 합니다
min_version string 협상할 최저 프로토콜: tls1.0, tls1.1, tls1.2, tls1.3. 비우면 기본값
max_version string 협상할 최고 프로토콜. 값은 동일하며 비우면 기본값
ciphers string TLS 1.2 이하용 OpenSSL 암호군 목록. 비우면 기본값
permissive bool 망가진/레거시 서버 상대: OpenSSL security level을 0으로 낮추고 재협상을 허용합니다
preset string 이름 붙은 브라우저 근사치: chrome, firefox, safari, curl. TLS 지문 참고
groups string 지원 그룹/커브와 그 순서. 예: X25519:P-256:P-384. 비우면 기본값
sigalgs string 서명 알고리즘과 그 순서. 예: ecdsa_secp256r1_sha256:rsa_pss_rsae_sha256
ciphersuites string TLS 1.3 스위트. ciphers로는 지정할 수 없습니다
alpn array 순서가 있는 ALPN 목록. 예: ["h2", "http/1.1"]. h2와 http/1.1만 허용. origin이 무엇을 고르든 gori가 그 프로토콜로 통신할 수 있어야 하기 때문입니다
session_tickets bool false면 hello에서 session_ticket 확장을 뺍니다. 생략 = OpenSSL 기본값(켬)
ocsp_stapling bool true면 status_request 확장을 추가합니다. 브라우저는 보내고 순정 OpenSSL은 보내지 않는 확장입니다. 생략 = 끔

min_version이 필요한 이유. gori는 기본 상태로 TLS 1.0/1.1만 지원하는 장비에 접근할 수 없고, verify_upstream: false로도 해결되지 않습니다. 이 설정은 인증서 검증을 끌 뿐 프로토콜 협상과는 무관합니다. Crystal의 TLS 클라이언트 컨텍스트가 생성자에서 TLS 1.0과 1.1을 비활성화하므로, 여기서 하한을 낮추는 것이 유일한 방법입니다. 레거시 장비는 보통 permissive: true도 함께 필요합니다. 배포판이 OpenSSL을 옛 암호군을 거부하는 security level로 빌드하기 때문입니다.

max_version이 필요한 이유. 하한만으로는 버전을 고를 수 없습니다. TLS 1.3도 지원하는 origin(요즘 origin은 전부 그렇습니다)에서는 하한을 아무리 낮춰도 핸드셰이크가 1.3으로 맺어지므로, min_version: "tls1.0"만으로는 대상이 아직 TLS 1.0을 받아 주는지 알 수 없습니다. OpenSSL의 암호군 목록은 TLS 1.2 이하에만 적용되므로 ciphers도 적용되지 않습니다. AES128-SHA로 TLS 1.2를 협상하려면 두 경계를 모두 지정하세요:

{ "host": "legacy.internal", "min_version": "tls1.2", "max_version": "tls1.2", "ciphers": "AES128-SHA", "permissive": true }

둘을 같은 값으로 고정하면 그 버전만 제안하므로, 핸드셰이크가 실패하면 대상이 그 버전을 받아 주지 않는다는 뜻입니다. min_version이 max_version보다 높으면 저장 시 거부됩니다. 그 조합은 제안할 버전이 없고, OpenSSL의 오류는 설정 파일이 아닌 origin을 가리키기 때문입니다.

인증서는 인라인 값이 아니라 파일 경로입니다. 개인키는 공유·내보내기 대상인 settings.json에 넣으면 안 됩니다(#439). 패스프레이즈가 걸린 키는 저장 시 거부됩니다. OpenSSL이 TUI가 점유한 터미널에 패스프레이즈를 물어 gori가 멈춘 것처럼 보이기 때문입니다. openssl pkey -in key.pem -out plain.pem으로 먼저 복호화하세요.

정책은 SNI 오버라이드가 아니라 접속한 호스트로 조회합니다. Repeater의 SNI 필드는 도메인 프론팅·vhost 테스트를 위해 다른 호스트 이름을 보낼 수 있기 때문입니다.

TLS 지문

gori를 거치면 origin이 보는 ClientHello는 브라우저가 아니라 gori의 OpenSSL 핸드셰이크입니다. 안티봇 스택은 그 핸드셰이크를 JA3/JA4 지문으로 식별해서, 브라우저에서는 되는 트래픽에 챌린지나 403을 내줍니다. 위 필드로 조정하고, 다음 명령으로 확인합니다:

gori settings tls-fingerprint

실제 dial이 만드는 것과 같은 TLS 컨텍스트에서, gori가 각 목적지로 보내는 ClientHello의 JA3/JA4를 출력합니다. OpenSSL은 협상 결과만 알려주므로, 이 설정은 이 명령으로 검증합니다.

{
  "outbound_tls": [
    { "host": "shop.example.com", "preset": "chrome" },
    {
      "host": "api.internal",
      "groups": "X25519:P-256",
      "sigalgs": "ecdsa_secp256r1_sha256:rsa_pss_rsae_sha256",
      "ciphersuites": "TLS_AES_128_GCM_SHA256:TLS_AES_256_GCM_SHA384",
      "alpn": ["h2", "http/1.1"],
      "ocsp_stapling": true
    }
  ]
}

프리셋은 근사치입니다. 프리셋은 분류기가 읽는 값 수준 필드를 전부 채웁니다. 암호군 목록과 순서, TLS 1.3 스위트, 지원 그룹, 서명 알고리즘, ALPN 쌍, session_ticket/status_request의 유무입니다. 하지만 브라우저의 JA3를 바이트 단위로 재현하지는 않으며, 할 수도 없습니다:

  • 확장 순서는 OpenSSL이 정하며, OpenSSL은 고정된 순서로만 내보냅니다. JA3는 그 순서를 해시합니다.
  • GREASE(RFC 8701) 배치도 OpenSSL이 정합니다. 두 지문 모두 GREASE 값을 걸러내지만, 브라우저가 GREASE를 끼워 넣는 위치는 OpenSSL이 고르는 위치와 다릅니다.
  • 포스트 퀀텀 키 셰어(X25519MLKEM768, 현재 Chrome·Firefox가 가장 먼저 제안하는 것)는 프리셋에서 뺐습니다. OpenSSL 3.5 이상에만 있는데, 프리셋은 구버전 빌드에서도 적용되어야 하기 때문입니다. 빌드가 지원한다면 규칙의 groups에 직접 넣으세요.
  • SHA-1 서명 알고리즘(Firefox와 Safari가 목록 맨 뒤에 레거시 폴백으로 아직 넣는 것)도 같은 이유로 뺐습니다. Debian·Ubuntu는 SHA-1 서명을 비활성화한 OpenSSL을 배포하므로, 넣으면 그 환경에서 프리셋 적용이 거부됩니다. 요즘 origin은 SHA-1을 고르지 않습니다.

다이제스트가 아니라 리포트가 출력하는 JA4_r 목록을 비교하세요. 어떤 필드가 아직 다른지 거기서 보입니다. 바이트 단위 일치는 확장 순서와 GREASE를 제어할 수 있는 TLS 스택(BoringSSL, rustls, uTLS)이 있어야 합니다. #822 3단계에서 다룰 일이고 이 필드의 범위 밖입니다.

규칙에 직접 적은 필드는 프리셋을 덮어씁니다. {"preset": "chrome", "groups": "P-521"}은 "Chrome 프리셋 + 내 그룹 목록"입니다.

ALPN과 두 개의 leg. gori는 그 소켓에서 쓸 프로토콜에 따라 다른 ALPN을 제안합니다. 복호화하는 터널에서는 h2를 제안하고, HTTP/1.1을 쓸 leg(평문 포워드 프록시 dial, Repeater, WebSocket)에서는 아무것도 제안하지 않습니다. 설정한 alpn 목록은 앞쪽에서는 그대로 쓰이고, 뒤쪽에서는 h2가 제거됩니다. 거기서 origin이 h2를 고르면 gori가 HTTP/2 연결에 HTTP/1.1을 써 넣게 되기 때문입니다. gori settings tls-fingerprint는 두 leg를 모두 보여줍니다.

잘못된 groups·sigalgs·ciphersuites·alpn 값은 그 문자열을 소비할 OpenSSL에 넘겨서 검사합니다. 이 테이블은 앱 안에 편집기가 없으므로(JSON을 직접 고칩니다) 검사는 시작 시점에 돌고, 규칙·설정·결과를 함께 알려 줍니다:

⚠ settings: outbound TLS `groups` is not a group list this OpenSSL accepts: X25519:P-257 — the rule for api.internal; TLS dials to that destination will fail

TUI에서는 같은 문장이 알림으로 뜹니다. 잘못된 규칙은 그 목적지에만 영향을 주며, 나머지 규칙과 gori의 다른 기능은 그대로 동작합니다.

이 테이블은 목적지 단위이고, 지문 A/B는 그렇지 않습니다. "이 엔드포인트가 chrome일 때와 curl일 때 다르게 답하나?"는 호스트 하나에 관한 질문이며, 전송 사이에 여기 규칙을 고치면 그 호스트로 가는 다른 모든 탭과 백그라운드 캡처의 핸드셰이크까지 함께 바뀝니다. Repeater 탭(␣Pt)과 fuzz 실행(--tls-preset)은 각자 자기 지문을 지정할 수 있고, 이 지문은 이 테이블을 건드리지 않고 dial 시점에 해석됩니다. 전송 단위 TLS 지문을 참고하세요. 그런 오버라이드는 ClientHello 모양만 교체합니다. 여기 설정한 client_cert/client_key, min_version/max_version, permissive는 그대로 적용됩니다.

인바운드 지문 위장(클라이언트의 핸드셰이크를 다른 것처럼 보이게 하는 것)은 이 섹션의 범위가 아닙니다. 여기서는 gori가 거는 연결의 모양만 다룹니다.

statusline

TUI 맨 아래에 선택적으로 추가되는 행입니다 (Preferences → General → Statusline). 활성화하면 gori가 일정 간격으로 셸 명령을 실행하고 그 stdout을 해당 행으로 렌더링합니다. Claude Code의 상태 표시줄에서 영감을 받은, 커스터마이즈할 수 있는 상태 바입니다. 기본값은 비활성화입니다. 변경하기 전까지는 이 섹션이 settings.json에서 생략됩니다.

{
  "statusline": {
    "enabled": true,
    "command": "date '+%H:%M'",
    "interval": 3,
    "timeout": 10
  }
}
Key Type Default Description
enabled bool false statusline 행 표시 여부
command string "" /bin/sh -c(Windows에서는 cmd.exe /d /s /c)로 실행되는 셸 명령. stdout의 첫 줄이 행이 됨. 비어 있으면 enabled여도 행을 잡지 않음
interval integer 3 실행 간격 초 (최소 1)
timeout integer 10 한 번의 실행이 종료되기까지 허용되는 초 (최소 1). interval보다 커도 됨

명령의 stdout에서 ANSI/SGR 색상 이스케이프(16색, 256색, truecolor, 볼드/밑줄 등)를 파싱하므로 색상이 있는 세그먼트를 만들 수 있습니다. 첫 줄만 사용됩니다. 출력은 터미널 너비로 잘립니다. UI를 막지 않습니다.

timeout은 interval과 별개입니다. 실행은 겹치지 않으므로(이전 실행이 끝난 뒤에야 다음 실행을 띄웁니다) interval보다 느린 스크립트는 할 수 있는 한 빨리 갱신됩니다. timeout을 초과한 실행은 종료되고 행은 ⋯ (timed out)이 됩니다.

편집은 즉시 반영됩니다. command · interval · timeout을 저장하면 현재 간격이 끝나기를 기다리지 않고 다음 프레임에 다시 실행합니다.

나머지는 Statusline 가이드에 있습니다. 실행할 때마다 stdin으로 받는 JSON 컨텍스트, 붙여 넣어 쓸 수 있는 명령과 각 명령이 만드는 행의 그림, 명령이 실패했을 때 행에 표시되는 내용을 다룹니다.

hostname_overrides

전역 다이얼 맵(충돌 시 프로젝트 레벨 오버라이드가 우선). /etc/hosts와 같은 개념입니다:

{
  "hostname_overrides": [
    { "host": "api.prod.internal", "ip": "10.0.0.42" },
    { "host": "api.prod.example", "ip": "127.0.0.1:8443" },
    { "host": "v6.internal", "ip": "[::1]:8443" }
  ]
}

값은 IP 리터럴이며 포트를 붙일 수 있습니다. 형식은 IP, IP:PORT, [v6]:PORT입니다. 포트 없는 IP는 요청 URL의 포트를 쓰며, 포트 지원 이전에 적힌 항목도 같습니다. 포트는 /etc/hosts에 없는 기능입니다. /etc/hosts는 바꿀 포트가 없는 리졸버가 읽습니다. 트래픽이 실제 브라우저나 모바일 앱에서 나와 gori가 URL을 쓰지 않을 때, https://api.prod.example/을 127.0.0.1:8443의 로컬 빌드로 보내는 데 쓰세요.

SNI, 인증서 호스트명, Host 헤더는 원래 이름을 유지합니다. TCP 연결 대상만 바뀝니다.

Preferences → Network & Tabs → Network → Host overrides에서, 또는 프로젝트별 항목은 Project 탭에서 편집합니다. Proxy & History를 참고하세요.

env

$ENV.TOKEN 같은 토큰은 Repeater, Fuzzer, Miner, Intercept, CLI, MCP에서 전송 시점에 확장됩니다(캡처되거나 잡힌 바이트에서는 직접 입력한 토큰만):

{
  "env": {
    "syntax": "namespaced",
    "prefix": "$",
    "vars": [
      { "key": "TOKEN", "value": "eyJhbGciOi…" }
    ]
  }
}
Key Type Default Description
syntax string "namespaced" 토큰 문법: namespaced(환경 변수 $ENV.KEY, 세션 바인딩 $BIND.NAME, 요청마다 새 값을 만드는 $GEN.NAME) 또는 bare($KEY, $NAME, 생성기 없음). 키가 없으면 그 파일이 네임스페이스보다 먼저 쓰였다는 뜻입니다. 다음 시작에서 namespaced를 채택하고, 전역 재작성 규칙을 다시 적고(settings.json.pre-namespaced-<타임스탬프> 복사본을 남깁니다), 키를 기록합니다. 각 프로젝트는 처음 열릴 때 저장된 토큰을 다시 적으며, 데이터베이스 옆에 백업을 남깁니다. bare는 옵트아웃이며 각 프로젝트를 되돌려 다시 적습니다. 전환은 gori settings env-syntax
prefix string "$" 토큰을 여는 시길 ($ENV.KEY), 두 문법 모두에서
vars array [] 전역 키/값 쌍. 프로젝트 변수(Project 탭 → ENV)가 충돌 시 우선

실행 중인 TUI나 gori mcp 서버는 다른 프로세스가 파일을 바꾸면 vars와 prefix를 다시 읽습니다. 다른 곳에서 교체하거나 삭제한 토큰은 재시작 없이 더 이상 나가지 않습니다.

user_agents

$GEN.USER_AGENT와 그 패밀리 이름이 쓰는 사용자 정의 목록입니다. 설정하면 내장 브라우저 목록을 대체하고, 없거나 비어 있으면 내장 목록을 씁니다.

{
  "user_agents": [
    "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/153.0.0.0 Safari/537.36",
    "Mozilla/5.0 (Macintosh; Intel Mac OS X 10.15; rv:156.0) Gecko/20100101 Firefox/156.0"
  ]
}

각 항목은 헤더에 그대로 들어가므로, 비어 있거나 제어 문자·보이지 않는 서식 문자가 들어 있는 항목은 불러올 때 경고와 함께 버려집니다. $GEN.USER_AGENT_CHROME / _FIREFOX / _SAFARI는 목록에서 해당 브라우저의 줄(Chrome/, Firefox/, 또는 둘 다 없는 Safari/)을 쓰고, 그런 줄이 없으면 내장 패밀리를 씁니다. Preferences → Editor & Keys → User-Agents 또는 gori settings user-agents로 편집합니다. env와 마찬가지로, 실행 중인 TUI나 gori mcp 서버는 다른 프로세스가 바꾼 목록을 재시작 없이 따라갑니다.

scan_rules

직접 만든 Probe 매치 규칙으로, 모든 프로젝트에 전역으로 적용됩니다. 프로젝트 범위 규칙은 프로젝트 데이터베이스에 저장됩니다. Probe → Rules → CUSTOM에서 편집합니다:

{
  "scan_rules": [
    {
      "id": "a1b2c3d4",
      "title": "Internal hostname leak",
      "description": "Build-server hostname in a response body",
      "side": "response",
      "region": "body",
      "kind": "regex",
      "pattern": "build-\\d+\\.corp\\.internal",
      "severity": "medium",
      "enabled": true
    }
  ]
}
Key Type Description
id string 생성 시 부여되는 무작위 hex 토큰
title string 발견 항목 제목
description string 발견 상세에 표시
side string request 또는 response
region string whole, header, body
kind string string, regex, 또는 exec(argv. 프로세스 훅 참고)
pattern string 매칭할 리터럴 또는 정규식, kind가 exec이면 실행할 명령
severity string info, low, medium, high, critical
enabled bool 규칙 실행 여부

파싱은 관대합니다. id, title, pattern이 없는 항목은 버려지고, 허용 범위를 벗어난 side / region / kind / severity는 로드를 실패시키는 대신 가장 안전한 값으로 대체됩니다.

retention

프로젝트가 보관하는 캡처 히스토리의 양입니다.

{
  "retention": {
    "max_flows": 100000
  }
}
Key Type Default Description
max_flows integer 100000 프로젝트당 보관할 최신 플로우의 최대 개수. 초과분은 오래된 것부터 삭제됩니다. 0 = 무제한

gori는 프로젝트 DB가 계속 커지지 않도록 항상 오래된 플로우를 정리해 왔습니다. 이전에는 컴파일 타임 상수였던 그 상한을 이 섹션에서 설정합니다. 기본값은 이전 값과 같으므로, 수정하기 전까지 동작은 달라지지 않습니다.

정리는 캡처 경로에서 수천 건의 insert마다 분산 실행되며, 삭제된 플로우의 WebSocket 메시지와 고아가 된 HTTP/2 프레임까지 연쇄 삭제합니다. 행을 삭제할 때마다 로그에 한 줄을 남깁니다.

상한을 넘는 프로젝트(나중에 내린 상한, 0으로 캡처한 프로젝트, 가져온 아카이브)를 열면, 정리가 지울 플로우 개수와 함께 알려 줍니다. TUI는 토스트와 알림 센터에, gori run capture와, 한 번 실행으로 정리가 시작될 만큼 플로우를 추가할 수 있는 gori run 명령(import, discover, fuzz --record-history)은 stderr에 한 번 남깁니다. 이 시점에는 아직 아무것도 지워지지 않았습니다. 초과분은 캡처가 새 플로우를 추가할 때마다 조금씩 지워지므로, 보존하려면 캡처하기 전에 상한을 올리고 프로젝트를 다시 여세요.

상한을 올리면 다음 프로젝트 열기부터 적용됩니다. 내리더라도 디스크가 바로 회수되지는 않습니다. prune은 DB 파일 내부의 페이지를 재사용 가능하게 만들 뿐 파일 크기를 줄이지 않으므로, 실제 파일 크기는 프로젝트 피커의 Compress(VACUUM 실행) 이후에 줄어듭니다.

캡처를 소유하지 않는 표면은 상한과 무관하게 prune하지 않습니다. gori mcp의 스토어, 삭제 미리보기용 개수 집계로만 여는 프로젝트, 새로 생성된 프로젝트가 여기에 해당합니다.

oast_providers

한 번 정의해두고 모든 프로젝트에서 재사용하는 OAST 프로바이더입니다. 프로젝트 전용 프로바이더는 프로젝트 데이터베이스에 저장되고, 여기 있는 것은 OAST 탭의 프로바이더 오버레이에서 scope를 global로 두고 추가하는 전역 목록입니다.

{
  "oast_providers": [
    {
      "id": "3f9a2c11",
      "name": "team interactsh",
      "kind": "interactsh",
      "host": "oast.example.com",
      "token": "…",
      "enabled": true
    }
  ]
}
Key Type Description
id string 생성 시 부여되는 무작위 hex 토큰. 직접 수정하지 마세요
name string OAST 탭에 표시되는 이름
kind string 프로바이더 종류: interactsh, custom-http, webhook.site, BOAST, postbin
host string 프로바이더 호스트
token string 프로바이더 인증 토큰(선택)
enabled bool 선택 가능 여부(기본값 true)

프로바이더를 추가하기 전까지 이 섹션은 기록되지 않습니다. id, name, kind, host가 빠진 항목은 로드할 때 버려집니다.

update

프로젝트 피커에 "update available" 한 줄 안내를 띄우는 시작 시 업데이트 확인입니다. gori가 자동으로 내보내는 유일한 외부 요청입니다. 설치는 gori update를 실행할 때만 합니다.

{
  "update": {
    "check_enabled": true,
    "notified_version": "0.2.0",
    "latest_seen": "0.2.0",
    "checked_at": 1753600000
  }
}
Key Type Default Description
check_enabled bool true false로 두면 확인을 건너뜀
notified_version string "" 이미 안내한 최신 버전. 릴리스당 한 번만 표시하기 위한 표식
latest_seen string "" 릴리스 피드에서 마지막으로 확인한 버전
checked_at integer 0 마지막 성공 확인의 unix 초. 하루 동안 결과를 캐시

뒤의 셋은 gori가 관리하는 상태이고, 직접 수정할 값은 check_enabled뿐입니다. 기본 설치에서는 섹션이 기록되지 않습니다.

fuzzer

Fuzzer의 Payload 오버레이가 기억하는 워드리스트입니다. 프로젝트 데이터가 아니라 임시 상태입니다. wordlist 카탈로그에 있는 목록은 이름(common.txt)으로 저장되고(작업 디렉터리에 같은 이름의 파일이 있어 이름이 그 파일을 가리키게 되면 경로로 저장), 이전 gori가 카탈로그 안의 절대 경로로 저장한 항목도 똑같이 읽힙니다. 그 밖의 경로는 입력한 대로 보관합니다.

{
  "fuzzer": {
    "recent_wordlists": ["/usr/share/wordlists/params.txt"],
    "favorite_wordlists": ["/home/me/lists/api.txt"]
  }
}
Key Type Description
recent_wordlists array 최근 적용한 워드리스트(카탈로그 이름 또는 경로). 최신순이며 최대 10개
favorite_wordlists array Path 필드에서 별표를 단 워드리스트(카탈로그 이름 또는 경로). 최근 목록보다 먼저 제안됨

워드리스트를 적용하거나 별표를 달기 전까지는 기록되지 않습니다.

redaction

안전한 증거 내보내기 프로파일, 활성 프로파일, 요청 없이도 적용할지 여부, 설치마다 하나씩 있는 자리표시자 비밀 키를 담습니다.

{
  "redaction": {
    "active": "pci",
    "default": true,
    "salt": "…16진수 64자…",
    "profiles": [
      {
        "name": "pci",
        "description": "이 engagement의 카드 소유자 데이터",
        "json_fields": ["card_number", "cvv"],
        "json_pointers": ["/data/acct", "/users/-/token"],
        "form_keys": ["cc"],
        "patterns": ["account=(\\d+)"]
      }
    ]
  }
}
Key Type Default Description
active string "" 호출에서 프로파일을 지정하지 않았을 때 안전한 내보내기가 쓰는 프로파일. 비어 있으면 내장 default
default bool false --redact 없이도 공유용 출력을 정제합니다. 켜 두면 --no-redact로 캡처한 바이트를 그대로 내보냅니다
salt string 자동 생성 모든 [REDACTED:<tag>] 뒤의 HMAC 키. 처음 쓸 때 한 번 기록되며 어떤 UI에도 표시되지 않습니다
profiles array [] 이름 붙은 규칙 묶음. name이 내장 프로파일과 같으면 그것을 대체합니다

각 프로파일은 name과 함께 description, json_fields, json_pointers, form_keys, patterns 중 필요한 것을 담습니다. 각 종류가 무엇을 매칭하는지는 run redact를 보세요. 파싱은 관대합니다. 쓸 수 있는 name이 없는 항목은 버려지고, 비어 있지 않은 문자열이 아닌 규칙 항목은 로드를 실패시키는 대신 건너뜁니다.

salt는 비밀이며, env의 토큰 값과 같은 조건으로 보관됩니다(디렉터리는 0700, 파일은 0600). 버리면 이미 쓴 산출물의 자리표시자가 모두 깨지므로 공장 초기화를 해도 salt는 남습니다. 인자 없는 gori settings export도 salt까지 가져가므로, 규칙만 건네려면 gori run redact profiles --format json을 쓰세요.

프로젝트 범위 프로파일은 프로젝트 데이터베이스에 있습니다. 프로젝트별 오버라이드를 보세요.

rewriter, colormarker, saved_views, decoder

이 네 섹션은 라이브러리를 담습니다. rewriter, colormarker, saved_views는 Match & Replace 규칙, History 색상 규칙, History 뷰의 전역 행입니다. 프로젝트는 자기 행을 프로젝트 데이터베이스에 따로 두고, 전역 행의 켜짐/꺼짐 상태도 거기서 오버라이드할 수 있습니다. decoder는 이름 붙인 Decoder 체인을 담습니다. 각 탭에서, 또는 gori run rewriter, gori run colormarker, gori run views에 --scope global을 붙여 만들고 편집하세요. 이 경로로 만들면 행마다 검증을 거칩니다. 기록되는 형태는 다음과 같습니다.

{
  "rewriter": {
    "next_rule_id": 3,
    "rules": [
      {
        "id": 1, "enabled": true, "name": "no CSP",
        "target": "response", "part": "head", "op": "remove_header", "match_kind": "literal",
        "pattern": "Content-Security-Policy", "replacement": "", "host": "", "body_file": ""
      },
      {
        "id": 2, "enabled": true, "name": "",
        "target": "request", "part": "head", "op": "short_circuit", "match_kind": "literal",
        "pattern": "/api/pay", "replacement": "", "host": "example.com", "body_file": "",
        "respond": "fault", "respond_args": "{\"fault\":\"reset\",\"delay_ms\":500}"
      }
    ]
  },
  "colormarker": {
    "next_rule_id": 2,
    "rules": [
      { "id": 1, "enabled": true, "name": "admin", "when": "path:/admin", "color": "teal", "style": "full" }
    ],
    "colors": [ { "name": "teal", "hex": "#2aa198" } ]
  },
  "saved_views": {
    "next_view_id": 2,
    "views": [ { "id": 1, "name": "APIs", "query": "path:/api" } ]
  },
  "decoder": {
    "chains": [ { "name": "myenc", "spec": "base64-encode > url-encode" } ]
  }
}

rewriter 규칙의 필드는 gori run rewriter add 플래그와 이렇게 대응합니다.

키 플래그 설명
id 전역 규칙 id. 프로젝트의 오버라이드는 이 id로 규칙을 가리킵니다
enabled --disabled 규칙의 기본 상태. enabled 키가 없는 규칙은 꺼진 것으로 읽습니다
name --name 규칙 목록에 보이는 라벨
target --target request 또는 response
part --part head, body, ws
op --op replace, add_header, set_header, remove_header, short_circuit, pipe, json_set, json_remove
match_kind --match literal 또는 regex
pattern --find 매칭할 대상, json 동작에서는 JSON 경로. pattern이 비어 있는 규칙은 파일을 읽을 때 버려집니다
replacement --value 치환 텍스트, 헤더 값, 미리 정한 응답, pipe 명령, 또는 JSON 텍스트로 쓴 json_set 값
host --host 호스트 glob. 비어 있으면 어디에나 적용됩니다
body_file --body-file, --map-dir short_circuit 규칙이 제공하는 파일, 또는 매핑하는 디렉터리
respond short_circuit 규칙이 답하는 방식: inline, file, dir, fault. body_file이 암시하는 값(있으면 file, 없으면 inline)이고 respond_args가 없으면 생략됩니다
respond_args --strip-prefix, --fallthrough, --fault, --delay, --hang 문자열로 저장된 JSON 객체. strip_prefix, fallthrough, fault(close/reset/hang), delay_ms, hang_ms를 담습니다

colormarker 규칙은 when(History QL 조건, --when), color(red, orange, yellow, green, blue, purple, 또는 colors에 있는 항목의 이름), style(full은 행 전체를 칠하고 strip은 한 칸만 칠함)을 담습니다. 색상 규칙은 트래픽을 건드리지 않으므로 enabled 키가 없으면 켜진 것으로 읽습니다. colors는 gori run colormarker color add --name --hex가 쓰는 사용자 팔레트이며, 이름이 비었거나 겹치거나 hex를 읽을 수 없는 항목은 버려집니다. saved_views 항목은 id, name, History QL query로 이루어집니다. decoder 체인은 name과 실행할 spec입니다. Decoder 탭의 Save chain by name이 기록합니다.

next_rule_id와 next_view_id는 늘어나기만 합니다. 프로젝트의 오버라이드는 전역 행을 id로 가리키므로, id를 재사용하면 옛 오버라이드가 새 규칙에 붙어 버립니다. 그래서 이 카운터는 규칙을 모두 지워도, 공장 초기화를 해도 남습니다. rewriter 규칙에서 이 gori가 모르는 라벨(더 새로운 빌드가 쓴 값)은 기본값으로 바뀌지 않고 적힌 대로 남아 규칙을 비활성 상태로 묶어 둡니다. 추가 키도 마찬가지입니다.

프로젝트별 오버라이드

프로젝트는 redaction 키 아래에 자체 리댁션 설정도 둘 수 있습니다. 자체 프로파일, 활성 프로파일, "기본으로 정제할지"의 자체 값(전역 기본값을 이 engagement에서만 끄는 명시적 false 포함)입니다. gori run redact가 기록합니다. 해석 순서는 프로젝트 → 전역 → 내장이고 이름이 같으면 먼저 나온 것이 우선합니다.

프로젝트는 전역 파일을 수정하지 않고도 자체 네트워크 설정을 고정할 수 있습니다. 이 값은 프로젝트 데이터베이스에 저장되며(키 net.bind_host, net.bind_port, net.upstream_proxy, net.upstream_destination_host, net.upstream_auth, net.connect_timeout_secs, net.io_timeout_secs, net.capture_max_mib), Project 탭의 Project settings 서브탭에서, 또는 헤드리스로는 gori run project network(list, get, set, unset)로 편집합니다. 아래의 요청 예산도 이 명령으로 설정합니다. .gori 아카이브에서 가져온 프로젝트(gori run project import)는 이 키와 프로젝트 호스트 오버라이드를 하나도 가져오지 않으므로, 이 머신의 전역 네트워크 설정으로 시작합니다.

Destination host는 프록시 라우팅을 대소문자를 구분하지 않는 호스트 패턴 하나로 제한합니다. 기본값 *는 모든 목적지를 프록시 대상으로 허용합니다. example.com은 해당 호스트와 서브도메인을 포함하고, *.example.com은 서브도메인만 포함합니다. 도메인, IPv4, IPv6 및 * 기반 IP 패턴을 사용할 수 있습니다. 일치하지 않는 목적지는 항상 직접 연결되며 upstream_rules나 network.upstream_proxy로 폴백하지 않습니다. 이 게이트는 프로젝트가 활성화된 동안 캡처, 재생, 스캐너, 업데이터 및 OAST 트래픽을 포함해 gori가 여는 모든 연결에 적용됩니다.

인증하려면 Upstream proxy 프로토콜을 고르고 Proxy host와 Proxy port를 입력한 뒤 Proxy auth를 켜고 Username과 Password를 입력합니다. SOCKS5는 대상 이름을 로컬에서, SOCKS5H는 프록시에서 해석합니다. HTTP는 Basic 인증을, 두 SOCKS 프로토콜은 RFC 1929 사용자명/비밀번호 인증을 사용합니다. NTLM은 지원하지 않습니다. 인증을 켜면 표시 중인 업스트림 주소가 전역 설정에서 상속된 값이더라도 항상 프로젝트에 고정됩니다. 따라서 나중에 전역 경로나 목적지 규칙이 바뀌어도 자격증명이 다른 프록시로 가지 않습니다.

비밀번호는 Password 행에 포커스가 있어 편집하는 동안 표시되고, 포커스가 벗어나면 다시 마스킹됩니다. 캡처된 engagement 데이터와 함께 소유자 전용(0600) 프로젝트 SQLite 데이터베이스에는 평문으로 저장됩니다. 프로젝트에 비밀을 저장하면 안 된다면 password_env를 쓰는 전역 upstream_rules 항목을 사용하세요. 일치하는 목적지에서는 잘못되거나 업스트림 주소 없이 남은 프로젝트 인증 값이 원 서버 연결 전에 fail-closed 처리됩니다.

타임아웃과 캡처 상한 키는 대상에 따라 달라지므로 프로젝트 단위입니다. 느린 내부 장비는 자체 유휴 타임아웃이, 아주 큰 응답을 주는 대상은 자체 캡처 상한이 필요하며, 다른 프로젝트의 값까지 올릴 필요는 없습니다.

요청 예산. outbound_max_rps와 outbound_max_requests는 engagement에서 합의한 상한을 프로젝트의 모든 gori 발신 요청에 걸쳐 지킵니다. Fuzzer, Miner, Sequencer, Discover, Repeater, retest, Probe의 능동 검사 등이 모두 포함되며, 같은 프로젝트 데이터베이스를 쓰는 모든 실행과 모든 프로세스(TUI, gori run, gori mcp)에 함께 적용됩니다. 실행의 --rate도 적용되며 둘 중 느린 쪽을 따릅니다. 송신은 속도 슬롯을 기다립니다. 총량이 소진되면 이후 송신은 모두 project request budget spent로 거부됩니다. 카운트는 outbound_max_requests를 설정한 시점부터 시작하며 unset하면 초기화됩니다. 프록시를 거치는 브라우저 트래픽은 세지도 지연시키지도 않습니다. 두 키는 프로젝트 전용(전역 값 없음)이며 gori run project network로 설정합니다.

어느 표면에 어느 키가 적용되는가. bind 키 둘은 gori가 리스닝 소켓을 여는 곳에서만 의미가 있습니다. 프록시 인증을 포함한 나머지 키는 gori가 밖으로 다이얼하거나 바디를 저장하는 모든 곳에 적용됩니다.

표면 bind_host / bind_port 업스트림 / 목적지 / 인증 / 타임아웃 / 캡처 상한
TUI (gori) 적용. 프록시가 고정된 주소로 리슨 적용
gori run capture 적용. 리슨하는 유일한 헤드리스 서브커맨드 (핀이 --listen/--port보다 우선) 적용
그 외 모든 gori run 서브커맨드 미적용. 바인딩하는 것이 없음 적용
gori mcp 미적용. 서버가 리슨하지 않음 적용

열려 있는 프로젝트의 유효 바인드 / 업스트림:

Priority Source
1 (최우선) 설정되어 있으면 프로젝트 DB net.bind_host / net.bind_port / net.upstream_proxy / net.upstream_destination_host / net.upstream_auth / 타임아웃 / 캡처 상한
2 CLI --listen / --port (전역 계층의 프로세스 한정 오버라이드)
3 settings.json network.*
4 (최하위) 공장 기본값 127.0.0.1:8070 / 직접 연결

현재 전역 값과 같은 Project 탭 필드를 저장하면 해당 KV 키가 삭제되므로, 프로젝트는 이후의 전역 변경을 계속 상속합니다. Destination host에는 전역 대응 값이 없습니다. 기본값 *를 저장하면 프로젝트 키가 삭제됩니다. gori run project network set은 키 하나를 지목하므로 전역과 같은 값이라도 고정하며(unset이 상속으로 되돌리는 방법입니다), 빈 upstream_proxy는 상속하는 대신 직접 연결을 고정합니다.

프로젝트와 데이터베이스

각 프로젝트는 최대 retention.max_flows개의 플로우를 보관합니다(기본 100,000, retention 참고). 그보다 오래된 것은 정리됩니다. 각 프로젝트는 SQLite 데이터베이스(crystal-db / crystal-sqlite3 사용)입니다. 여기에는 플로우, WebSocket 메시지, 스코프 규칙, 이슈, match 규칙, HTTP/2 프레임, repeater 및 fuzz 세션, 호스트 오버라이드, sitemap 태그, miner 세션, Probe 이슈가 담기고, 플로우 본문의 전문 검색 인덱스도 들어 있습니다. 저장하는 요청/응답 본문은 network.capture_max_mib(기본 2 MiB)로 상한이 걸려 있습니다. 더 큰 본문은 데이터베이스에서 잘리지만 실제 와이어 크기는 기록됩니다. --db PATH로 어떤 프로젝트의 데이터베이스든 직접 엽니다. gori run과 gori mcp는 --project NAME으로 이름이 지정된 프로젝트도 고를 수 있습니다.
